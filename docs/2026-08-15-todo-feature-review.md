# 검토 — 전망형 개인 일정관리("내일 할 일") (2026-08-15)

로드맵(`docs/2026-08-06-role-roadmap.md` §2)이 미착수로 남긴 전망형 계획 기능 검토. **구현/목업 지시 아님** — 코드·목업 변경 없음.

## 핵심 결론

- **DailyNote(회고형)와 데이터는 재사용 불가, 화면 컴포넌트·htmx 배선은 재사용 가능.** 결정적 차이: 회고형은 "이월 없음"이 확정 사항인데, 전망형은 이월(밀린 일 처리)이 핵심 기능이다. 상태(완료/미완) 필드도 회고형엔 아예 없다. `type` 컬럼으로 한 테이블에 합치는 안은 기각 — 모든 쿼리에 분기가 붙고, "완료 체크한 예정이 자동으로 기록이 되나?"라는 질문이 다시 생기는데 이건 **v2에서 이미 반려된 승격 메커니즘**과 같은 문제다.
- **스코프는 최소안 권고**: `id / dueDate / text / done` 4필드, 우선순위·반복·알림·캘린더 그리드는 전부 배제(알림은 폐쇄망 로컬 앱이라 앱을 안 켜두면 애초에 못 알림). 이월이 필요하면 `dueDate`를 실제로 고치지 말고 **조회 시점에만** 오늘로 끌어와 보여주는 쪽 — 원래 며칠 밀렸는지가 안 지워짐.
- **기존 `ReportItem`의 예정일 필드(개발완료일 등)와는 완전히 별개로.** `CarryOverService`가 매주 `ReportItem`을 복제하면서 일정 필드를 비우기 때문에, FK로 엮으면 매주 고아가 되거나 중복된다.
- **배치는 대시보드 우측 스택에 카드 하나** — 4번째 탭 신설, 히스토리 탭 편입 전부 기각(히스토리는 과거 축이라 미래 목록과 안 맞음, 좌측 회고 카드 옆에 두면 v2 승격 논쟁 재현).
- **어휘 분리 필수**: "기록"은 회고형 전용, 전망형은 "할 일"/"예정" 중 하나만. 시간 라벨도 "기록된 시간"과 "예상 시간"을 헷갈리지 않게 분리. 두 목록을 한 화면에 나란히 두지 않는다.

## 사용자 결정 (2026-08-15 확정)

| 질문 | 결정 |
|---|---|
| 1. 기능 필요한가? | **필요함** — "내일 혹은 금주에 무엇을 해야 할지" 작성하는 용도(하루 단위 + 주 단위 둘 다) |
| 2. `.md` 내보내기 포함? | **불포함** — 일반적인 개인 TODO 리스트, 보고 데이터 아님 |
| 3. 못 지킨 일 처리 | **자동 이월 없음** — 날짜에 그대로 두고 표시만(지난 날짜임을 강조 표시) |
| 4. 완료 시 "한 일 기록"으로 이동? | **아니오, 완전히 별개** |
| 5. 추가 필드 | **우선순위만 추가.** 예상소요시간·반복일정은 없음 |

→ 최소 스코프안이 확정됐다: `id / dueDate / text / done / priority`. 이월 로직 불필요해져 구현이 한 단계 더 단순해짐(§2의 안 B는 기각, 안 A + 우선순위로 확정).

다음 단계는 design 라운드(대시보드 우측 스택 카드 목업)로 넘어가는 것 — 사용자 승인 후 착수.
