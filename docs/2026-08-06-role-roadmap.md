## 1. 역할별 기능

`docs/idea,md`와 `docs/project-handoff-summary.md` §2를 합쳐 정리한다. "현재 상태" 열은 2026-08-06 기준 이 앱의 구현 여부다.

| 역할 | 기능 | 현재 상태 |
|---|---|---|
| 파트원 | 최소한의 동작으로 주간 업무·투입공수 입력, `.md` 내보내기 | **구현됨** — 지금 앱이 곧 이 부분 |
| 파트원 | **개인 일정관리** | **회고형만 구현됨(2026-08-15, 일일 기록)** — 전망형("내일 할 일")은 미구현·스펙 없음 (§2) |
| 파트장 | 본인 주간보고를 파트원과 **동일하게** 관리 | 파트원 기능 재사용 전제 — 역할 개념이 없어 미구현 |
| 파트장 | 파트원 주간보고를 **복사-붙여넣기로 취합**해 주간 단위 파트 보고 생성 | 미구현 |
| 팀장 | 본인 주간보고를 파트원과 동일하게 관리 | 위와 동일 |
| 팀장 | **파트원 단위 추적관찰**(인물별 이력 조회) | 미구현 |
| 팀장 | **프로젝트성 일감의 투입공수 조회** | 미구현 |

- 파트장/팀장이 "본인 보고는 파트원과 동일"이라는 건, 세 역할이 **같은 입력 화면·같은 데이터 모델을 공유**하고 그 위에 역할별 조회/취합 기능이 얹히는 구조라는 뜻이다. 역할마다 입력 화면을 따로 만드는 게 아니다.
- 취합 방식은 **복사-붙여넣기로 확정**됐다(아래 소절). `project-handoff-summary.md` §2/§7의 "md 업로드" 서술은 이 결정으로 대체된다.

### 파트장/팀장의 취합 플로우 (2026-08-06 확정)

사용자가 실제 업무 동선을 구체화했다. 파일을 주고받는 게 아니라 **사내 위키를 경유**한다.

1. 파트원이 이 프로그램으로 작성 → `.md` 파일 생성(우리 v2 스키마 그대로).
2. 그 `.md` 파일을 **NHN Dooray**(회사 협업툴) 위키의 **개인 폴더에 업로드**.
3. 파트장이 Dooray 위키에 들어가 **뷰어로 렌더링된 화면을 복사**해서 본인 PC(파트장 프로그램)에 **붙여넣기**로 가져온다.
4. 팀장이 파트장의 요약본을 가져올 때도 **동일한 복사-붙여넣기 절차**.

즉 프로그램이 받는 입력은 `.md` 파일이 아니라 **위키 뷰어에서 복사된 렌더링 결과**다. 이게 §5-3의 기술 과제를 만든다.

### 이 플로우에 새로 필요한 기술 구성요소

셋 다 현재 앱에 없다. 파트장 기능 착수 시 신설해야 한다.

| # | 구성요소 | 요지 |
|---|---|---|
| (a) | **붙여넣기 캡처 UI** | 평범한 `<textarea>`는 `text/plain`만 받아 서식이 날아간다. `contenteditable` 영역이나 paste 이벤트를 직접 가로채는 방식으로 만들어 클립보드의 **`text/html`** 쪽을 읽어야 한다 |
| (b) | **HTML→마크다운 변환기** | 자바 쪽 후보: flexmark-java의 html-to-markdown 모듈. **폐쇄망이라 로컬 vendor 필요**(htmx.min.js를 저장소에 직접 넣어둔 것과 같은 제약) |
| (c) | **변환 결과 미리보기/검증 UI** | 변환 직후 "이렇게 파싱됩니다"를 보여주는 단계. 기존 작성 화면의 md 미리보기 모달과 같은 패턴으로 두면 된다 |

## 2. 파트원 개인 일정관리 (2026-08-15 갱신 — 회고형은 해소됨)

`docs/idea,md`의 "자신의 스케줄 관리도 할 수 있으면 좋을 것 같다" 한 줄이 근거의 전부였다. 이후 별도 기획 라운드(`docs/2026-08-06-daily-notes-design-worklog.md`)에서 "일일 기록(DailyNote)" 기능으로 구체화·구현됐고, 2026-08-15에 앱에 반영됐다.

**단, 해소된 범위는 절반뿐이다:**

| 이 항목이 암시하던 것 | 상태 |
|---|---|
| **회고형** — 날짜별로 한 일을 짧게 남기고 나중에 훑어보기(+선택적 투입시간) | ✅ **해소** — 대시보드/작성 화면 좌측 패널/히스토리 "한 일 기록" 서브뷰 세 곳에서 CRUD, `.md` 내보내기 미포함, 주간보고 통계와 완전 분리 |

## 3. ⚠️ 아키텍처 결정 변경 — 역할별 별도 프로그램이 아니라 "같은 앱 안에서 역할 전환"

`docs/project-handoff-summary.md` §3은 파트원/파트장/팀장을 **각자 로컬 H2를 소유한 별도 프로그램**으로 구상했고, 프로그램 간 데이터 교환은 오직 `.md` 파일 + 메일이었다.
사용자가 이번 대화에서 이 구상을 뒤집었다: **하나의 앱 안에서 역할을 전환**하는 방식으로 간다. §3의 해당 서술은 이 결정으로 대체된다.

유지되는 것은 그대로다 — 폐쇄망, `.md` 파일 교환, fat jar + `.bat` 실행, 로컬 H2.

### 이 변경이 backend에 의미하는 것

- **이 앱에는 사용자/역할/인증 개념이 아예 없다.** `AppSettings`는 `SINGLETON_ID` 고정의 1인용 싱글턴이고, 거기 있는 `role` 필드는 권한이 아니라 화면에 찍히는 **단순 표시용 문자열**이다.
- 따라서 역할 전환을 하려면 최소한 (1) 사용자를 식별하는 개념, (2) 역할을 권한/화면 분기로 쓰는 구분자가 새로 필요하다. **`AppSettings` 싱글턴 구조로는 표현할 수 없으므로** 새 엔티티(또는 기존 엔티티의 소유자 구분 컬럼) 도입이 불가피하다.
- 파급이 큰 지점: `WeeklyReport`·`Project`가 지금은 "이 PC의 유일한 사용자 것"이라는 암묵적 전제 위에 있다. 파트장이 파트원 보고를 취합해 자기 DB에 적재하는 순간 **모든 조회에 소유자 필터가 필요**해진다. 이건 스키마 마이그레이션을 동반하는 변경이므로 §5의 미결 사항이 정리되기 전에는 착수하지 않는다.

## 4. 단계적 전환 계획

`docs/project-handoff-summary.md` §3의 1→2단계 계획을 유지하되, 이번에 제약 하나를 새로 추가한다.

| 단계 | 구동 방식 | 저장 | 인증 | 상태 |
|---|---|---|---|---|
| 1단계 | 로컬 PC에서 Java fat jar + `.bat` 기동, 폐쇄망 | 로컬 H2 (`~/.weekly-report/data/db`) | 없음 (역할 전환 방식 미정 — §5-2) | **현재** |
| 2단계 | 사내 웹서버 게시 (허가 필요) | 서버 DB | 로그인 + RBAC | 미착수 |

### ⚠️ 신규 제약 — 로컬 데이터의 웹서버 이관 경로

사용자가 이번에 명시한 조건: **1단계에서 로컬에 쌓인 데이터를 2단계 웹서버로 옮길 수 있어야 한다.**

- 이건 "지금 H2를 버리고 다른 저장 방식으로 바꾸라"는 뜻이 **아니다.** 지금 저장 방식은 그대로 두되, 앞으로의 설계 결정이 이관 가능성을 막지 않아야 한다는 **제약 조건**이다.
- 구체적 메커니즘은 **미정**이다(§5-6). 후보만 적어둔다 — H2 데이터 자체를 마이그레이션, 기존 `.md` 내보내기를 이관 매개로 재활용(이미 사람이 읽는 본문 = 파싱 대상인 단일 텍스트라 왕복 가능성이 있음), 별도 bulk import API. `.md`를 매개로 쓰는 안은 v2 마크다운 파서를 전제하는데, **그 파서는 어차피 §5-3(파트장 취합)에서 먼저 필요해진다** — 두 과제가 같은 부품을 공유하므로 순서를 함께 고려할 것.

## 5. 다음에 정할 것 (미결 — 구현 착수 전 필수)

아래 항목은 **아직 사용자 결정이 없다.** 임의로 답을 채우지 말 것.

1. **파트원 개인 일정관리 — 전망형만 남음(2026-08-15)**. 회고형(날짜별 기록+열람+시간)은 일일 기록으로 해소됐다(§2). "내일 할 일"류 전망형 요구가 다시 나오면 데이터 모델(완료 vs 예정)부터 새로 정해야 하며, 기존 일정 필드(개발완료일/테스트예정일/배포예정일, 휴가)와의 관계도 그때 함께 결정한다. 별도 기획 세션 필요.
2. **"같은 앱 안에서 역할 전환"의 구체적 방식** — 로그인이 필요한가, 아니면 폐쇄망 + 로컬 실행이니 단순 역할 선택 드롭다운(온보딩에서 역할 지정)으로 충분한가. 1단계에서 어디까지 갖출지가 §3의 새 엔티티 설계를 좌우한다.
3. **파트장의 "복사-붙여넣기 취합" 로직** — 플로우 자체는 §1에서 확정됐고(Dooray 위키 뷰어 → 복사 → 붙여넣기), 남은 건 **렌더링된 복사본을 어떻게 마크다운으로 되돌리느냐**다. 접근 방향은 아래로 정리됐으나 아직 구현·검증 전이다.
   - **되돌리는 것 자체는 가능하다.** 브라우저 클립보드는 복사 시 `text/plain`과 `text/html` **두 형태를 동시에** 담는다. 위키 뷰어에서 복사하면 `text/html` 쪽에 실제 마크업(`<h2>`, `<ul><li>`, `<strong>` 등)이 실려 온다.
   - 그 HTML을 HTML→마크다운 변환기(§1 표의 (b))로 돌려 v2 스키마 마크다운으로 재구성한다. 항목 줄(`- {티켓} : {제목} [구분] — {시간}h · {일수}일 · {완료율}%`)은 위키에서 특수 서식이 걸리지 않는 **일반 텍스트**라 변환 과정에서 내용이 그대로 보존된다 — 헤더/목록 같은 **구조만 복원되면 된다**.
   - 변환 직후 "이렇게 파싱됩니다" 미리보기(§1 표의 (c))로 검증 단계를 두는 게 안전하다.
   - **v2 마크다운 파서가 여기서 처음 필요해진다** — 현재는 내보내기만 있고 읽어들이는 쪽이 없다.
   - 그 위에서 **붙여넣은 여러 파트원 보고를 어떻게 파트 합산 보고로 합치는지**(중복 처리, 프로젝트 축 병합, 요약 초안 생성)는 여전히 미정.
4. **⚠️ Dooray 위키의 실제 렌더링 마크업이 시맨틱한지 검증** (미결 3번의 선행 조건, **사용자가 직접 확인해야 하는 항목**) — 위키가 마크다운을 `<h2>`·`<ul><li>` 같은 시맨틱 태그로 렌더링하는지, 아니면 스타일만 입힌 `<div>`/`<span>` 범벅인지에 따라 변환 품질이 갈린다. 후자면 변환기만으로는 구조 복원이 어려워 별도 전처리가 필요하다. **실제 Dooray 위키 페이지에서 복사해 브라우저 개발자도구로 클립보드 HTML을 확인해봐야 확실해진다 — 아직 검증 안 됨.**
5. **팀장의 "프로젝트별 투입공수" 집계** — 어떤 화면/쿼리로 보여줄지. 프로젝트 축 집계라 현재의 주차 축 조회와 다른 접근이 필요하다.
6. **로컬→웹서버 데이터 이관 메커니즘** (§4).
7. **`docs/project-handoff-summary.md` 원본 처리 방침** — 이 로드맵에 맞춰 원본을 고칠지, 아니면 이 문서를 최신본으로 두고 원본에는 각주로만 대체 표시할지. (이미 §3 "역할별 별도 프로그램"과 §5.5 "제출된 보고서는 고정" 두 군데가 현재 정책과 어긋나 있어, 원본의 신뢰도 표시 방식 자체를 한 번 정리할 필요가 있다.)

## 6. 현재 앱 범위와의 관계

**이 문서는 향후 방향이고, 지금 앱의 범위를 바꾸지 않는다.**

- 현재 앱과 하네스의 backend/frontend/qa 에이전트는 여전히 **파트원 화면만** 다룬다. CLAUDE.md 최상단의 "파트원용 주간 업무보고 프로그램", "파트원 화면만 확정, 파트장/팀장 화면은 범위 밖" 서술은 그대로 유효하다.
- 진행 중인 다른 작업(대시보드 랜딩 재기획 — `docs/2026-08-06-dashboard-redesign-planning.md`)도 파트원 화면 범위 안의 일이므로 이 로드맵과 충돌하지 않는다.
- 이 문서가 실제 구현으로 이어지는 시점은 §5의 미결 항목이 사용자 결정으로 정리된 뒤다.
