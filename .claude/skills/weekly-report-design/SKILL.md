# Weekly-Report Design — UI/UX 기획 가이드

## 디자인 시스템 (design/weekly-report-mockup.html이 원본, 여기 요약은 참고용)

새 컴포넌트를 만들기 전 반드시 목업 파일의 `<style>` 블록을 직접 열어 확인한다 — 아래는 자주 쓰는 값 요약이며 전체가 아니다.

**색상 토큰** (오클치, 라이트 전용 고정):
```
--bg oklch(98% .005 250)        페이지 배경(연회색)
--surface oklch(100% 0 0)       카드/입력 배경(흰색)
--surface-sunken oklch(97% .006 250)   hover/포커스 시 살짝 어두운 배경
--border-soft oklch(94% .008 260)      카드 테두리(얇게)
--text / --text-muted / --text-faint   본문/보조/희미한 텍스트 3단계
--accent oklch(55% .16 260)     단일 포인트 블루 — 이 프로젝트엔 포인트 컬러가 이거 하나뿐이다
--warn-bg/--warn-fg             이월 배지(주황 계열)
--good-bg/--good-fg             완료 배지(초록 계열)
--danger-bg/--danger-fg         삭제/위험 액션
```
새 상태 색상이 필요하면 이 팔레트 안에서 고른다 — 임의로 새 색상을 도입하지 않는다.

**간격/모양 스케일**: 카드 `border-radius:18px`, 버튼/입력 `8~12px`, 배지/토글류는 `999px`(완전 pill). 카드 패딩 `26px 28px`. 그림자는 거의 안 쓰고(`--shadow`는 1px 미세 그림자), hover 시에만 `--shadow-sm`이 살짝 붙는다 — **입체감보다 얇은 보더로 구획을 나누는 게 이 시스템의 기본기**다.

**타이포**: 본문 14px, 라벨/보조 텍스트 11~13px, 카드 제목 15px(font-weight 600), 통계 수치 26px(font-weight 700, letter-spacing -.02em). 시스템 폰트 스택(`-apple-system, "Segoe UI", "Malgun Gothic", "Apple SD Gothic Neo"` 등) — 웹폰트 로드 안 함(폐쇄망이라 외부 폰트도 못 씀).

**인풋 = "텍스트처럼 보이다 hover/focus 시 강조"** — 이 시스템에서 가장 중요한 인터랙션 규칙이다. 평상시 `border:1px solid transparent`(안 보임), hover 시 `background:var(--surface-sunken)`, focus 시 `border-color:var(--accent)` + 배경 강조. 즉 입력 필드가 폼처럼 각지고 튀어 보이지 않고 텍스트에 자연스럽게 섞여 있다가, 만질 때만 "여기 입력 가능하다"는 걸 보여준다. 새 입력 필드를 디자인할 때 이 패턴을 기본으로 삼는다(예외가 필요하면 왜 다른 스타일이 필요한지 근거를 남긴다).

**"+추가" 고스트 버튼**: 보더 없이 `color:var(--text-muted)`인 텍스트 버튼(`.ghost`), hover 시에만 배경+accent 색으로 강조. 새 항목 추가 카드 자체는 `1.5px dashed var(--border)` 점선 테두리로 "여기 누르면 새로 생긴다"를 암시한다. 강한 CTA(예: "제출")만 `.btn`(꽉 찬 accent 배경)을 쓰고, 그 외 부가 액션은 고스트/아웃라인을 쓴다 — 화면에 진한 버튼이 여러 개 있으면 이 시스템의 위계가 깨진다.

**카드 = 기본 단위**: 프로젝트/기타/휴가 등 그룹은 전부 흰 카드(`--surface`, 얇은 보더, 큰 라운드)로 감싼다. 새 정보 블록을 추가할 때 카드 바깥에 떠 있는 요소를 만들지 않는다.

## 목업 갱신 절차

1. `design/weekly-report-mockup.html`을 Read로 전체 확인 — 이 파일은 `<style>` + 마크업 + vanilla JS(상태 배열 조작)로 이루어진 자체완결 SPA다. **JS 로직은 목업 안에서만 쓰는 것**이고 실제 앱(frontend 에이전트)이 그대로 이식하진 않는다는 걸 전제로 편집한다.
2. 새 화면/컴포넌트는 기존 스타일 블록의 클래스(`.card`, `.row`, `.ghost`, `.btn`, `.badge` 등)를 최대한 재사용한다. 새 클래스가 꼭 필요하면 위 색상 토큰/스케일을 그대로 쓰고, 새 오클치 값을 만들지 않는다.
3. 갱신 후 `Artifact` 도구로 발행한다 — HTML 파일이므로 그대로 publish 가능. 파비콘/제목 등은 기존 목업 관례(제목 `주간업무보고 · 디자인 목업`)를 유지한다.
4. 사용자 피드백을 받으면 목업을 다시 고치고 재발행한다(같은 파일 경로로 Artifact를 다시 호출하면 같은 URL이 갱신된다).
5. 사용자가 승인하면 그제서야 frontend에게 "이 목업을 참고해 Thymeleaf+htmx로 구현하라"고 넘긴다.

## frontend와의 경계 (중요)

목업은 **시각 스타일과 정보구조의 기준**이지 **구현 방법의 기준이 아니다**. frontend 에이전트는:
- 색상 토큰, 카드/인풋/버튼 스타일, 레이아웃 구조는 목업 그대로 따른다
- 목업의 `<script>`(상태 배열, `data-*` 이벤트 위임 등 클라이언트 SPA 로직)는 절대 이식하지 않는다 — 실제 앱은 서버 렌더링+htmx로 그 책임을 대체한다

이 경계를 설계 근거에 명시해두면 frontend가 "목업이 이렇게 동작하니까 JS도 그대로 베끼면 되나?"로 헷갈리지 않는다.

## 기존 확정 IA (재검토하지 말고 존중할 것)

- 화면은 대시보드/작성/히스토리 3탭(2026-08-15 대시보드 재도입, 첫 진입은 대시보드). 주차 페이저는 작성 탭에서만 노출
- 프로젝트 카드는 헤더(프로젝트명+일감번호)만 있고, 그 아래 바로 세부 항목 목록 — 일감 블록 wrapper 없음
- 항목 입력 행 컬럼 헤더는 항목이 하나라도 있을 때만 노출
- 일정 상세 패널: 개발완료일→테스트예정일→배포예정일 순으로 세로 스택, 비고는 마지막
- 다크모드 없음(라이트 톤 고정)

새 화면을 기획할 때 이 IA를 깨는 게 정말 필요한지 먼저 자문한다. 필요하다면(예: 화면이 너무 커져서 탭이 하나 더 필요하다) 왜 기존 구조로 안 되는지 설계 근거에 명시하고, 이런 근본적 IA 변경은 사용자 승인 없이 frontend로 넘기지 않는다.
