# Weekly-Report Docs-Sync — 문서 동기화 가이드

## 문서 지도와 신뢰도

| 문서 | 역할 | 신뢰도 |
|---|---|---|
| `CLAUDE.md` | 살아있는 소스 오브 트루스. 배경/결정/정책/함정/미결 사항 | **최신 — 항상 우선** |
| `docs/weekly-report-md-schema.md` | `.md` 내보내기 포맷 상세 스펙 | 코드와 대조 필요 — `MdExportService` 변경 시 드리프트 발생 |
| `docs/project-handoff-summary.md` | 원본 설계 요약(배경·목표·조직구조·데이터모델·화면구성) | **부분적으로 낡음** — "제출 후 고정" 규칙 등 폐기된 정책을 아직 담고 있음. CLAUDE.md의 각주로만 폐기 표시된 상태, 원본 자체는 미수정 |
| `docs/2026-08-02-frontend-port-worklog.md` | 목업→Thymeleaf 이식 작업 로그 | 과거 시점 기록 — 갱신 대상 아님(작업 로그는 사후 수정하지 않는다) |

`project-handoff-summary.md`처럼 원본 설계 문서 자체를 다시 쓸지, 아니면 CLAUDE.md 각주로 폐기 표시만 계속 쌓을지는 **아직 사용자가 결정하지 않은 사항**이다(CLAUDE.md "다음에 할 일" 참고). 이 스킬을 쓰는 에이전트가 임의로 원본을 대대적으로 재작성하지 않는다.

## CLAUDE.md 갱신 절차

1. **"다음에 할 일" 절 확인** — 이번 변경이 그 절의 항목을 해결했으면, 항목을 제거하고 그 결정/구현 요지를 위쪽 관련 섹션(기술 스택/프론트엔드/알아두면 좋은 것 등)에 흡수시킨다. 새로 생긴 미결 사항은 같은 포맷(불릿 + "진행 시 손댈 곳" 하위 목록)으로 추가한다.
2. **정책이 뒤집혔으면 명시적으로 기록** — 이 프로젝트는 이미 한 번 "제출된 보고서는 고정" → "항상 수정 가능"으로 정책이 뒤집힌 전례가 있고, 그때 "⚠️ 중요한 정책 변경" 콜아웃 + "이 결정으로 폐기됨"이라는 표현으로 남겼다. 유사한 정책 반전이 생기면 같은 패턴(굵게 콜아웃 + 무엇이 왜 폐기됐는지 + 어떤 문서가 아직 옛 내용을 담고 있는지)을 재사용한다.
3. **날짜를 붙인다** — 새 섹션/항목에는 `YYYY-MM-DD` 기준일을 명시해 나중에 상대적 시점 판단이 가능하게 한다.
4. **코드에서 유추 가능한 내용은 쓰지 않는다** — 패키지 구조, 파일 목록, 클래스명 나열처럼 `Read`/`Grep` 한 번으로 알 수 있는 내용은 CLAUDE.md에 새로 추가하지 않는다. CLAUDE.md는 "왜 이렇게 결정했는지"만 담는다.

## `docs/weekly-report-md-schema.md` 갱신 절차

1. `MdExportService`의 실제 출력(헤더 2행 `{역할} · {yyyy.MM.dd (요일)} ~ ...`, 그룹 순서: 프로젝트→개발→기타→휴가, 라인 포맷 `- {티켓} : {제목} [구분] — {시간}h · {일수}일 · {완료율}%`, 일정 하위 불릿, 합계 라인)을 코드에서 직접 확인한다 — backend 에이전트의 요약에만 의존하지 말고 실제 라인 예시로 검증한다. `MdExportServiceTest`의 assert 문자열이 가장 빠른 대조 기준이다.
2. 스펙 문서의 각 섹션이 이 출력과 라인 단위로 일치하는지 대조하고, 다르면 스펙을 코드에 맞춰 갱신한다(코드가 스펙에 맞춰 고쳐진 경우가 아니라면).
3. **`<!--DATA...DATA-->` JSON 블록은 2026-08-05자로 제거됐다**(스펙 문서 v2). 이제 사람이 읽는 본문과 파싱 대상이 같은 텍스트라, 본문 포맷 변경은 곧 파트장/팀장 프로그램과의 계약 변경이다 — `MdExportService`가 바뀐 PR에서 스펙 문서가 함께 안 바뀌었으면 그건 드리프트가 아니라 계약 파손으로 다루고 반드시 동기화한다.

## 에스컬레이션 기준

다음 경우는 문서를 스스로 고치지 말고 리더/사용자에게 확인을 요청한다:
- 정책 자체가 아직 결정되지 않았는데 문서화를 요청받은 경우 (예: dev 그룹 티켓 필수 여부, `Project.active` 집계 방식)
- `docs/project-handoff-summary.md` 원본을 통째로 재작성해야 할 만큼 낡은 경우
- backend/frontend의 변경 요약만으로는 정책 의도가 불분명한 경우
