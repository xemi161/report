# 대시보드 v7 벤토 — 확정안 반영 (v3)

사용자 결정: **"②번 벤토로 가되 최근 2주 맨위크와 진행중인 프로젝트를 빼줘"**
대상 파일: `design/weekly-report-mockup.html` (순수 목업 레이아웃 변경. 서버/EntryService 로직과 무관)

## 1. 뺀 것 / 남긴 것

**뺀 것 — 하단의 큰 타일 2개뿐**
- `.t-mw` "최근 2주 평균 맨위크" (34px 대형 숫자 + 주별 막대 브레이크다운)
- `.t-proj` "진행중인 프로젝트" (프로젝트별 이름·티켓·진행률 막대 목록)

**그대로 남긴 것 — 상단 지표 타일 4개(`.t-metric`, 40px 숫자)는 전부 유지**
`이번 주 시간` / `이번 주 맨위크` / `기한 지난 할 일` / `진행중 프로젝트`

즉 **두 정보가 앱에서 사라진 게 아니라, 이 화면에서 "상세 브레이크다운"만 사라졌다.**

| 정보 | 상세(뺀 것) | 남아 있는 곳 |
|---|---|---|
| 맨위크 | 최근 2주 평균 + 주별 막대 | 지표 타일 `이번 주 맨위크`(낮으면 danger 색), 히스토리 탭의 보고서별 맨위크(`.hist-metric`), 작성 탭 상단 통계 |
| 진행중 프로젝트 | 프로젝트별 이름·티켓·진행률 막대·최근 보고 주차 | 지표 타일 `진행중 프로젝트` = **건수 + 평균 진행률** |

`activeProjects()` 판정 규칙(active AND 최근 진행률 < 100%, 진행률 = 세부 항목 완료율의 **평균**)은 손대지 않았다 — 실제 앱 `EntryService.activeProjectsWithProgress()`와 계속 일치해야 하므로. 목업은 이제 그 결과의 `length`와 평균만 쓴다.

## 2. 그리드 재계산 (14행 → 10행)

`.bento`는 12컬럼 × `grid-auto-rows:62px`, `gap:14px`, `auto-flow`는 **sparse**(dense 아님).

**변경 전 (DOM 순서: hero → metric×4 → daily → todo → mw → proj)**
```
행 1-4   : hero(6×4)          | metric 4개(3×2 ×4 = 6칸 2×2)
행 5-10  : daily(8×6)         | todo(4×10) ┐
행 11-14 : mw(4×4) proj(4×4)  |            ┘
총 14행
```

**mw/proj만 DOM에서 지웠을 때 (= 하지 않은 안)**
todo가 `span 10`을 유지해 행 5-14를 계속 점유 → **행 11-14의 col 1-8이 아무도 안 채우는 빈 구멍**.
sparse auto-flow라 뒤 타일이 앞으로 끌려오지도 않는다(뒤 타일 자체가 없다). 구멍 크기 = 4행 + 내부 gap 3개 = `4×62 + 3×14 = 290px`.

**적용한 안 — `.t-todo{grid-row:span 10 → span 6}`**
```
행 1-4   : hero(6×4)  | metric 4개 (3×2 ×4)
행 5-10  : daily(8×6) | todo(4×6)
총 10행
```
auto-placement 추적(검증 완료):
1. hero → 행 1-4, col 1-6
2. metric×4 → 행 1-2 col 7-9 / 행 1-2 col 10-12 / 행 3-4 col 7-9 / 행 3-4 col 10-12
3. daily(span 8) → 행 1-4엔 8칸 연속 자리가 없어 커서가 넘어가 **행 5-10, col 1-8**
4. todo(span 4) → 커서 위치에서 col 9-12 비어 있음 → **행 5-10, col 9-12**
→ 행 10에서 정확히 끝난다. **빈 구멍 없음.**

**픽셀 검증**
| | 계산 | 값 |
|---|---|---|
| 벤토 전체 (before) | `14×62 + 13×14` | 1050px |
| 벤토 전체 (after) | `10×62 + 9×14` | **746px** (−304px) |
| `.t-todo` (before) | `10×62 + 9×14` | 746px |
| `.t-todo` (after) | `6×62 + 5×14` | **442px** (`.t-daily`와 동일) |

> 지시서에 적힌 "746px→372px"는 스팬 내부 gap 5개(70px)를 빼먹은 값 — 실제는 442px이다. 결론(span 6이 맞다)은 동일.

TODO 목록은 `.tile-body{flex:1; min-height:0; overflow:auto}`라 세로가 줄어도 안쪽에서 스크롤만 늘어난다. `TODO_VISIBLE = 8`은 그대로 뒀다 — 이 값은 "접힘 상태에서 몇 건까지 보여줄까"이지 타일 높이와 연동된 값이 아니고, 넘치는 부분은 스크롤이 받는다.

## 3. daily / todo를 같은 높이(6행)로 맞춘 이유

**위계가 흐려지지 않는다고 판단한 근거:**
- v7의 위계는 원래 "면적 = 사용 빈도"였는데, 중간 타일이 빠진 지금은 **띠(band) 2개**가 그 일을 대신한다. 위 띠(hero + 지표 4, 4행) = *이번 주가 어떤 주인가*, 아래 띠(daily + todo, 6행) = *지금 뭘 적고 뭘 해야 하나*. 아래 띠가 화면 높이의 6/10을 가져가는 것 자체가 "여기가 매일 손대는 자리"라는 신호다.
- 두 타일의 차이는 이제 **세로가 아니라 가로(8칸 vs 4칸)**로 난다. 오늘 한 일은 입력 줄 + 여러 필드가 들어가 가로가 필요하고, TODO는 한 줄짜리 항목의 세로 목록이라 좁아도 된다 — 폭 차이가 콘텐츠 형태와 맞아떨어져서 오히려 자연스럽다.
- 모자이크가 "균일한 격자"로 회귀할 위험은 위 띠가 막는다. `6×4` + `3×2 × 4`의 엇갈림이 그대로라 v6에서 지적받은 "눈에 탁 띄지 않는다"는 문제로 돌아가지 않는다.

**검토했지만 택하지 않은 대안**
| 대안 | 기각 이유 |
|---|---|
| todo `span 10` 유지 + daily를 `span 10`으로 늘림 | daily가 746px가 되는데 하루치 기록은 보통 2~4건이라 대부분 빈 여백. "큰 타일 = 자주 쓰는 것"이 "큰 타일 = 빈 것"으로 뒤집힌다 |
| daily를 12칸 전폭으로, todo를 그 아래 전폭으로 | 벤토가 아니라 그냥 세로 스택이 된다. 사용자가 고른 게 ②번 벤토인데 벤토성을 잃는다 |
| 빈 4행에 새 타일 추가 | 사용자는 "빼줘"라고만 했다. 스코프 확대 |

## 4. 실제로 고친 곳 (`design/weekly-report-mockup.html`)

- `.bento` 위 주석 블록: ASCII 배치도를 10행 구조로 다시 그리고, **왜 14→10행인지 / TODO span을 왜 같이 줄여야 하는지**를 계산 근거로 남김(이 프로젝트는 계산값 CSS에 근거 주석을 다는 관례가 있다 — 작성 탭 `.split`의 680/916/1670과 같은 취급). 두 지표가 화면에서만 빠진 것이지 앱에서 없어진 게 아니라는 점도 명시.
- `.t-todo` `span 10` → `span 6` (인라인 주석: "6 = .t-daily와 동일. 이 둘은 항상 같이 움직인다")
- `.t-mw` / `.t-proj` 규칙 삭제
- 미디어 쿼리 2곳(`max-width:1180px`, `max-width:700px`)에서 `.t-mw`/`.t-proj` 선택자 제거
- 죽은 컴포넌트 CSS 삭제 — `.bar`(가로 진행률 막대), `.mw-big/.mw-sub/.mw-weeks/.mw-week*`, `.proj-row/.proj-top/.proj-meta`. 이 파일이 컴포넌트 스타일의 source of truth라 죽은 클래스를 남기면 frontend가 살아 있는 것으로 읽는다. 자리에 삭제 사유 주석을 남겼고, 되살릴 일이 생기면 직전 리비전에서 그대로 가져오면 된다. **hero의 세로 막대 `.wk-day .bar-v`는 별개라 그대로 유지.**
- `renderDashboard()`: `recent`/`avg`/`avgLow`/`weekRows`/`projectRows` 계산과 두 타일의 템플릿 리터럴 삭제. `projects = activeProjects()`는 지표 타일이 쓰므로 유지
- 상수 `RECENT_WEEKS_FOR_AVG` 삭제(유일 사용처였음). `LOW_MANWEEK_THRESHOLD`는 지표 타일이 계속 사용
- 작성 탭의 스테일 주석("추세 지표는 대시보드로 옮겼고") 갱신 — 평균 맨위크를 작성 탭으로 되돌리지 말라는 이유("이 자리는 지금 이 주를 보는 곳")를 함께 적음
- `activeProjects()` doc 주석: 이제 건수·평균만 쓴다는 점과, 판정 규칙은 실제 앱과 계속 일치해야 한다는 점 추가

JS는 `node --check`로 파싱 검증 완료. 파일 2258줄 → 2217줄.

## 5. qa/frontend를 위한 검증 가능한 기준

- 대시보드 벤토 타일은 **정확히 6개**: hero 1 + 지표 4 + 오늘 한 일 1 + TODO 1 = 7개(hero/지표/daily/todo). 그 아래 `.bento-foot`에 과거 보고서 타일 1개 별도
- 벤토 총 높이 746px(1180px 초과 뷰포트 기준), 오늘 한 일과 TODO의 상단·하단이 **픽셀 단위로 정렬**돼야 한다
- "최근 2주 평균 맨위크"·"진행중인 프로젝트"라는 **제목을 가진 카드가 대시보드에 없어야** 한다. 단 지표 타일의 `진행중 프로젝트`(건수)와 `이번 주 맨위크`는 **있어야** 한다
- 1180px 이하에서 벤토가 6컬럼으로 접히고 모든 `grid-row`가 풀린다(`grid-row:auto !important`), 타일 안쪽 스크롤도 꺼진다

## 6. 상태

- **아직 구현 승인 전.** 이번 라운드는 design 단독이고 backend/frontend/qa는 호출하지 않았다.
- 이 세션엔 `Artifact` 도구가 없어 발행하지 않았다 — 오케스트레이터가 스크린샷으로 사용자에게 제시한다.
- frontend에게 넘어갈 때 상기시킬 것: 목업의 **시각/구조만** 기준이고 `<script>`의 상태 배열·렌더 로직은 이식하지 않는다. 실제 앱에선 서버가 계산해 Thymeleaf로 렌더하고, 이 그리드는 `app.css`의 `.bento` 계열 규칙으로만 옮기면 된다.
