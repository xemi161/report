## 0. 이번 라운드에서 뒤집힌 것

사용자 피드백:

> 체크해서 주간업무로 등록할때 복잡할거 같아 프로젝트에 들어갈지, 개발/기타에 들어갈지 정리하기 모호하고
> 요일마다 입력을 다르게 한다면 합치는 기능도 모호할거 같아

이 지적은 v2 §4 전체(승격 메커니즘)의 근거를 무너뜨린다. v2는 목적지 모호성을 **프로젝트명 문자열 매칭 + 대상 셀렉트로 되돌리기**라는 장치로 덮으려 했는데, 그건 "모호함을 UI로 관리하겠다"는 답이지 모호함을 없앤 게 아니다. 그리고 "월·화·수에 나눠 적은 기록 3건이 주간보고 항목 1건에 대응한다"는 다대일 관계는 v2 설계에 아예 표현조차 없었다(체크는 항상 1:1로 새 항목을 만들었다).

**확정된 방향**: 체크박스·자동등록을 **완전히 제거**하고, 일일 기록은 **순수 참고 자료**로만 둔다.

```
[이번 주에 한 일]              [주간보고 작성]
—————————————           —————————————
월 GTPP 결제로그 분석          (기존 작성 폼 그대로)
화 2차인증 문의대응
수 위키 정리

(추가/삭제만 가능, 화살표/체크없음)
```

사람이 왼쪽을 **보면서** 오른쪽 폼에 항목을 **직접** 만든다. 다대일 합치기는 사람 머릿속에서 일어나며,
프로그램은 그 판단에 개입하지 않는다 — 애초에 프로그램이 대신 판단할 수 없다는 게 이 피드백의 요지다.

**부수 효과 하나(개선)**: v2에서는 보고서가 없는 주에 체크박스가 잠겼는데, 이제 그런 상태가 없다.
**보고서를 만들지 않은 주에도 기록은 그대로 쓰고 고칠 수 있다.** 기록이 주간보고에 의존하지 않게 됐기 때문이다.

## 1.1 남은 것

- 날짜별 그룹 목록(금~목, 오름차순, 기록 있는 날 + 오늘만 표시), `오늘` 칩
- 텍스트 추가 / 수정 / 삭제
- 하단 상시 노출 입력 한 벌(날짜 선택 + 텍스트) — 지난 날 빠뜨린 기록 채우기
- 대시보드 "오늘 한 일" 빠른 입력(피드백 대상 아니었음, 그대로)
- 좌우 분할, 패널 sticky, `숨기기`/`한 일 기록 보기` 토글

## 1.2 컴포넌트 변경 하나 — 한 줄 input → 줄바꿈 textarea (`.d-txt`)

역할이 "조작 대상"에서 "**읽는 자료**"로 바뀌었으므로, 텍스트가 잘리면 기능의 목적 자체가 깨진다.
`<input type=text>`는 좁은 패널에서 긴 기록(예: "GTPP 결제 로그 분석 — 타임아웃 원인 확인" ≈ 300px)을
가로로 잘라버린다. `rows="1"` textarea + 내용 높이 자동 확장으로 바꿨다.

- 스타일 규칙은 그대로: 평상시 테두리 없음 → hover `--surface-sunken` → focus `--accent` 보더.
- Enter는 줄바꿈이 아니라 편집 종료(blur). 기록은 한 줄짜리 메모라는 전제를 유지한다.
- **frontend 주의**: 자동 높이 확장은 서버가 못 하는 클라이언트 동작이라 `static/js/app.js` 담당
  (완료율 100% "완료" 배지와 같은 자리). 이게 부담이면 고정 2줄 textarea로 떨어뜨려도 설계 의도는 지켜진다.

## 2. 좌우 분할 폭 재계산 — `body.wide`는 **여전히 필요하다**

패널이 단순해졌으니 340px를 줄이고, 나아가 전역 폭 확장(v2 §3)을 되돌릴 수 있는지 실제로 계산했다.

### 2.1 패널: 340px → **300px**

사라진 가로 요소는 체크박스 18px + gap 8px = **26px**뿐이다(대상 셀렉트는 본문 아래 줄이라 폭에 영향 없음).
340 − 26 = 314 → 텍스트 줄바꿈 여유를 조금 더 주고 **300px**로 확정.

### 2.2 그런데 `body.wide`는 되돌릴 수 없다 (계산)

항목 행(`itemRow`) 1줄의 최소 폭:

```
ticket 132 + phase 96 + "시간" 28 + hours 56 + "·" 10 + days 40 + "일" 17
  + pct-wrap 85 + chevron 23 + trash 25            = 512
+ gap 8 × 10                                        =  80
+ title-input 최소                                  = 160
                                                     ----
                                                      752   (배지 없음)
+ 완료 배지 48 + gap 8                              =  808
+ 이월 배지 44 + gap 8 (이월+완료 동시)             =  860
```

기본 폭(`main{max-width:1140px}`, 좌우 패딩 28) → 콘텐츠 1084px.
분할 시 우측 컬럼 = 1084 − 18(gap) − 300(패널) = **766px**, 카드 패딩 56을 빼면 행에 쓸 수 있는 폭 **710px**.

**752px에도 못 미친다.** 게다가 이월 배지는 초안 생성 시 이월 항목마다 붙으므로 예외가 아니라 정상 상태다
(860px 필요). 따라서 **되돌리면 행이 상시로 두 줄이 된다** — "한 줄 = 한 항목"이라는 이 화면의 기본 시각 규칙이 깨진다.

### 2.3 대신 확장 폭을 줄였다: 1400px → **1360px**

패널이 40px 좁아진 만큼 페이지 확장도 40px 줄인다. 결과적으로 **우측 작성 폼 컬럼의 실폭은 v2와 완전히 동일**하다
(1360 − 56 − 18 − 300 = 986px, 카드 내부 930px → 배지 2개 붙어도 제목 칸 230px 확보).
불필요한 전역 변경을 남기지 않되, 이미 검증된 폼 폭은 건드리지 않는 선택이다.

```css
body.wide main{max-width:1360px;}
body.wide .header-inner{max-width:1340px;}
.split{grid-template-columns:minmax(0,300px) minmax(0,1fr); gap:18px;}
```

`body.wide`가 붙는 조건은 v2와 같다(작성 탭 + 패널 표시 중일 때만).
→ **QA 검증 기준**: 대시보드·히스토리·"패널 숨김" 상태의 작성 화면은 기존과 **픽셀 단위로 같은 1140px**이어야 한다.

## 3. 대시보드 좌우 균형 — 문제는 폭이 아니라 **높이**였다

사용자: *"둘다 같은 사이즈가 되도록 오늘 한 일 영역이 더 커야될꺼 같아."*

### 3.1 진단

v2 그리드는 `1fr | 340px`라 좌측이 이미 **2배 이상 넓었다.** 그런데도 작아 보인 이유는 세로다:

- 우측 스택 = 맨위크 카드(34px 큰 숫자 + 주별 바 2개) + 진행중 프로젝트 카드 → 세로로 길다
- 좌측 "오늘 한 일" = 입력 한 줄 + 오늘 기록 1~2건 → 짧게 끝나고 아래가 텅 빈다

즉 **좌측 카드가 우측보다 훨씬 일찍 끝나서** 넓지만 작아 보였다. 폭을 더 주는 것만으로는 안 고쳐진다.

### 3.2 조치 3가지

1. **높이를 맞춘다** — `.dash-grid{align-items:stretch}` + `.dash-side{align-self:start}`.
   좌측 카드가 우측 스택의 아래 끝까지 늘어난다. 우측 두 카드는 자기 높이를 유지한다(같이 늘어나면 빈 카드가 된다).
   → **두 컬럼이 같은 가로선에서 끝난다** = 사용자가 말한 "둘 다 같은 사이즈".
2. **늘어난 공간이 빈칸으로 안 보이게** — `.dash-daily{display:flex; flex-direction:column}` +
   `.dash-daily .daily-foot{margin-top:auto}`. 요약 줄이 카드 **바닥에 고정**되고, 남는 공간은 목록과 요약 사이에 놓인다.
   헤더-목록-푸터로 프레이밍되므로 "빈 카드"가 아니라 "채워질 자리"로 읽힌다.
   부수 효과로 기록이 하루 사이 늘어도 카드 높이가 출렁이지 않는다.
3. **실제 내용을 조금 더 채운다** — `DASH_RECENT_DAYS` 3 → **4**(오늘 + 기록 있는 최근 3일).
   늘어난 높이를 데모/실사용 모두에서 실제 기록으로 메운다.

추가로 사이드 컬럼을 **340px → 320px**로 20px 줄여 좌측을 그만큼 넓혔다(맨위크·프로젝트 행은 세로 스택이라 320px에서 깨지지 않음).

**검증 기준**: 900px 초과 뷰포트에서 "오늘 한 일" 카드의 아래 테두리와 "진행중인 프로젝트" 카드의 아래 테두리가
**같은 y좌표**에서 끝나야 한다. 900px 이하에서는 세로 스택으로 떨어지며 stretch가 해제된다(`align-items:start`).

## 4. 문구 정리 (완료형 방어선 유지)

| 위치 | v2 | v3 |
|---|---|---|
| 대시보드 카드 하단 | `이번 주 N건 · 미반영 M건` | `이번 주 기록 N건` |
| 대시보드 카드 하단 링크 | `작성 화면에서 정리하기 →` | `주간보고 쓰면서 보기 →` |
| 작성 화면 패널 안내 | "체크하면 오른쪽 주간보고에 …추가됩니다" | "오른쪽 주간보고를 쓸 때 참고하는 목록입니다. 기록이 항목으로 자동 옮겨지지는 않습니다." |

마지막 문구는 **기대치 관리가 목적**이다. 목록이 보고서 옆에 붙어 있으면 "체크하면 옮겨지나?"를 시도하게 되는데,
한 줄로 미리 못박아 헛짚는 시도를 없앤다.

**v2 §6의 방어선은 그대로 유지** — UI 문구를 전부 완료형("한 일")으로 통일했고 "일정/할 일/예정" 같은
전망형 어휘를 쓰지 않는다. 로드맵 §2 "파트원 개인 일정관리"와 이름이 충돌하지 않게 하기 위해서다.

## 5. backend 파급 — **v2 §8을 통째로 대체**

v2 §8(승격 로직, `promotedItem` FK, 연결 무결성, 티켓 필수 강제)은 **전부 해당 없음**. 새 요구사항은 이게 전부다:

### 5.1 엔티티 하나, 순수 CRUD

```
DailyNote
  id        Long
  workDate  LocalDate    -- 기록 대상 날짜(작성 시각 아님: 어제 걸 오늘 적을 수 있다)
  text      String       -- 자유 텍스트 한 줄
  createdAt Instant
```

- **`ReportItem`·`WeeklyReport`·`Project` 어느 것과도 연관관계가 없다.** FK 없음, cascade 없음, 무결성 훅 없음.
- 소속 주는 저장하지 말고 `workDate`에서 파생 — 주 정의(금~목)는 이미 `WeekLabelService`에 있다.
  `weekStart`를 중복 저장하면 주 정의 변경 시 동기화 버그가 생긴다.
- 필요한 쿼리는 **하나**: `findByWorkDateBetweenOrderByWorkDateAscIdAsc(start, start+6)`.
  대시보드·작성 화면 둘 다 이걸 쓴다. `workDate` 인덱스면 충분(주당 수십 건).
- 엔드포인트 3개: 추가 / 텍스트 수정 / 삭제.

### 5.2 기존 로직에 영향 없음

- `EntryService` 항목 추가·수정·삭제, 제출 검증, `CarryOverService` 이월 — **손댈 것 없음**
- `MdExportService` / `docs/weekly-report-md-schema.md` — **손댈 것 없음**(일일 기록은 `.md`에 안 나감, §6 열린 질문 유지)
- `ReportItem` 삭제 시 되돌릴 연결 상태가 없다 → v2 §8.4의 `ON DELETE SET NULL` 요구 소멸

### 5.3 ⚠️ CLAUDE.md "개발 그룹 티켓 필수 여부"는 **이 기능과 무관해졌다**

v2 §8.3은 이 미결 항목을 강제로 밀어냈다 — 승격으로 만들어지는 개발 항목은 항상 티켓이 비어 있어서,
티켓 필수가 유지되면 기능 자체가 성립하지 않았기 때문이다. **v3에는 자동 생성 항목이 없다.**
사용자가 오른쪽 폼에서 직접 항목을 만들고 티켓도 직접 입력하므로, 현행 검증(project/dev 모두 티켓 필수)을
그대로 둬도 이 기능은 정상 동작한다.
→ 그 미결 항목은 **원래의 독립된 UX 결정으로 되돌아간다**(승인된 목업에 티켓 없는 개발 항목 예시가 있고
md v2 포맷도 티켓 없는 줄을 지원한다는, 이 기능과 무관한 근거로만 판단하면 된다).

## 7. 그대로 유효한 v2 결정 (재확인만)

- **3탭 유지** — 일일 기록 전용 탭 없음(v2 §5). 과거 기록은 작성 탭 주차 페이저로 열람.
  참고 전용이 되면서 독립 탭을 만들 이유는 오히려 더 줄었다.
- **대시보드 블록 구성 4개** — hero / 오늘 한 일 / 맨위크 + 진행중 프로젝트 / 과거 보고서 5개. 제거·강등 없음.
- **기록 입력 지점은 대시보드 + 작성 화면 둘 다**(v2 §2). 다만 이제 둘의 기능 차이는 **범위뿐**이다
  (대시보드 = 오늘 + 최근 3일 / 작성 화면 = 그 주 7일). v2의 "기록은 어디서나, 승격은 작성 화면에서만"이라는
  역할 분담은 승격이 사라지면서 무의미해졌다.
- **다크모드 없음**, 새 오클치 값 없음, 기존 토큰만 사용.

## 8. frontend 경계 (승인 후 착수 시)

**아직 착수 금지.** 승인되면 아래를 함께 전달할 것:

- 목업 `<script>`의 `DAILY` 배열·이벤트 위임은 **이식하지 않는다**(기존 원칙 그대로).
- **기록 추가/삭제는 "구조가 바뀌는 동작"** → 기존 규약대로 `#writeView` 전체를 다시 렌더해 `hx-swap="outerHTML"`.
- **기록 텍스트 수정만 `hx-trigger="change" hx-swap="none"`** — 포커스 유지 목적, 기존 인라인 필드와 동일.
- **대시보드 빠른 입력**은 전체 재렌더가 아깝다 — `hx-swap="beforeend"`로 행만 덧붙이고 입력값을 비우는 편이 낫다
  (포커스가 아예 안 날아감). 하단 `이번 주 기록 N건`은 `hx-swap-oob`로 같이 갱신.
- **textarea 자동 높이**는 `app.js` 담당(§1.2).
- v1 §6 주의(작성 탭 통계는 인라인 편집 시 `hx-swap="none"`이라 낡음 → `app.js` 클라이언트 계산)는 **그대로 유효**.
