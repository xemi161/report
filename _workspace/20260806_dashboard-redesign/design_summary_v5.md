## 0. 이번 라운드의 요청과 결론

> 사용자: **"주간보고 작성시 이번 주에 한 일 영역이 지금보다 100% 더 커졌으면 좋겠어"**

**결론: 요청대로 340px → 680px(정확히 2배)로 키웠다. 다만 폭을 고정하지 않고 유동으로 만들었다** —
680px는 화면 폭이 1670px 이상일 때 나오는 값이고, 그보다 좁은 화면에서는 우측 항목 행이 두 줄로
깨지지 않는 선까지만 자동으로 줄어든다(1536px 노트북에서 530px).

| 화면 폭(CSS px) | 좌측 패널 | 우측 컬럼 | 항목 행 |
|---|---|---|---|
| **1670px 이상** (2560 모니터, 1920@100%) | **680px (요청대로 정확히 2배)** | 916px↑ | 한 줄 ✅ |
| 1536px (1920 모니터 @125% 배율) | **530px (+56%)** | 916px | 한 줄 ✅ |
| 1281~1536px | 291~530px (연속 변화) | 916px | 한 줄 ✅ |
| 1280px 이하 | 세로 스택(폭 경쟁 없음) | 전체 폭 | 한 줄 ✅ |

v4에서는 **1274px 미만에서 행이 두 줄로 깨졌는데, v5에서는 그 구간이 사라졌다** — 폭이 모자라면
행이 접히는 대신 패널이 줄어들기 때문이다. 즉 이번 변경은 패널을 키우면서 동시에
"한 줄 = 한 항목" 규칙이 지켜지는 폭 구간을 **넓혔다**.

## 1. 폭 계산 (v4 §2와 같은 방식)

### 1.1 우측 컬럼의 하한은 860px이 아니라 **916px**이다

v3에서 실측한 값은 **항목 행(`itemRow`) 자체**의 최소 폭이다:

```
배지 없음                                    752px
+ 완료 배지 44 + gap 8                       804px
+ 이월 배지 44 + gap 8 (완료+이월 동시)      860px   ← 이월은 초안 생성 시 항목마다 붙는 정상 상태
```

행은 카드 안에 들어가고 `.card{padding:26px 28px}` → **좌우 56px**. 따라서

```
우측 컬럼 하한 = 860(행) + 56(카드 패딩) = 916px
```

> v4에서 우측 컬럼 986px는 행에 930px를 줘서 배지 2개가 붙어도 제목 칸이 230px 남는 상태였다.
> v5에서 916px로 내리면 **제목 칸이 최소값 160px까지 좁아질 수 있다** — 단, 그건
> **완료+이월 배지가 동시에 붙은 행에서만** 이고, 배지 없는 일반 행은 여전히 268px를 갖는다(§3.1).

### 1.2 정확히 2배(680px)에 필요한 페이지 폭

```
56(main 좌우 패딩) + 680(패널) + 18(gap) + 916(우측 하한) = 1670px
→ body.wide main{max-width:1400px}  →  1670px
```

### 1.3 1670px은 현실적인가 — **절반만 그렇다** (그래서 유동으로 만들었다)

이 개발기의 디스플레이를 실측했다:

| 디스플레이 | 물리 해상도 | **CSS 폭** |
|---|---|---|
| 주 모니터 | 2560x1440 | **2560px** → 1670px 여유 있게 들어감 ✅ |
| 보조(노트북) | 1920x1080 @125% 배율 | **1536px** → 1670px **안 들어감** ❌ |

Windows 10에서 1920x1080 노트북의 기본 배율이 125%라 **CSS 폭이 1536px밖에 안 되는 환경은
사내에서 흔한 경우다**(파트원 PC 사양은 확인 못 했지만, 이 개발기의 보조 화면이 이미 그렇다).

`max-width`는 화면이 그보다 **좁을 때는 아무것도 지켜주지 못한다** — 1536px 화면에서
패널을 680px로 못 박으면 우측 컬럼이 `1536−56−18−680 = 782px`(행 726px)로 내려가
**860px 하한을 못 넘겨 이월 배지가 붙은 행이 전부 두 줄로 깨진다.** 그것도 조용히.

### 1.4 그래서: 우측 하한을 먼저 보장하고 남는 폭을 패널이 전부 가져간다

```css
body.wide main{max-width:1670px;}          /* 넓은 화면에서 패널이 680px에 도달하는 폭 */
body.wide .header-inner{max-width:1650px;} /* main보다 항상 20px 작은 기존 관계 유지 */
.split{grid-template-columns:minmax(0,680px) minmax(916px,1fr); gap:18px;}
@media (max-width:1280px){ .split{grid-template-columns:1fr;} }
```

- `minmax(0,680px)` — 패널은 **680px까지만** 커지고, 폭이 모자라면 **자기가 대신 줄어든다**.
- `minmax(916px,1fr)` — 우측 컬럼은 **916px 밑으로 절대 안 내려간다** = 행이 안 접힌다.
- 두 규칙이 만나 §0 표의 연속적인 동작이 나온다. 미디어쿼리 단계(점프)가 아니라 연속 변화라,
  화면 폭이 얼마든 **그 화면에서 가능한 최대 패널 폭**을 항상 쓴다.

### 1.5 세로 스택 경계를 1040px → **1280px**로 올렸다

스택 경계 바로 위에서 패널이 얼마나 남는지 계산하면:

```
패널 폭 = 뷰포트 − 56 − 18 − 916
  1281px → 291px    1041px → 51px(사용 불가한 조각)
```

v4 그대로 1040px에 두면 1041~1100px 구간에서 패널이 **50~110px짜리 세로 조각**이 된다.
v3에서 검증한 패널 하한이 300px이므로, **패널이 290px 밑으로 내려가는 1280px 미만은 세로 스택**으로 넘긴다.

> 이 구간(1040~1280px)은 v4에서는 "좌우 분할이지만 항목 행이 두 줄로 깨진 상태"였다.
> v5에서는 "세로 스택 + 행은 한 줄"이 된다 — 어느 쪽이든 v4보다 규칙을 더 잘 지킨다.

**스택 시 패널 폭 제약은 다르다(질문에 대한 답)**: 세로로 쌓이면 좌우 폭 경쟁 자체가 없어져
패널은 그 화면의 콘텐츠 폭을 통째로 쓴다(680px 상한은 `grid-template-columns`에만 걸린 값이라
스택 시에는 적용되지 않는다). **이건 v3·v4와 동일한 동작이고 이번에 바꾸지 않았다.**

## 2. 넓어진 폭을 무엇에 쓰는가 (여백이 아니라 밀도로)

패널만 넓히고 내부를 그대로 두면 "커진 게 아니라 헐렁해진 것"이 된다. 실제로 늘어나는 건 셋이다.

### 2.1 기록 텍스트: 191px → **약 530px (2.8배)**

```
680 − 40(패널 패딩 20x2) − 56(시간) − 12(단위 h + 여백) − 25(🗑) − 18(gap 6x3) = 529px
```

v4의 191px는 **긴 기록이 2줄로 감기는 폭**이었다(예: "GTPP 결제 로그 분석 — 타임아웃 원인 확인").
530px에서는 이런 기록이 **한 줄에 들어간다.** 이게 단순한 시각적 여유가 아닌 이유:

> 패널은 `position:sticky` + `max-height:calc(100vh − 108px)`로 **높이가 화면에 묶여 있다.**
> 기록당 줄 수가 2줄→1줄로 줄면 **스크롤 없이 보이는 기록 수가 그만큼 늘어난다.**
> 이 패널의 목적이 "주간보고를 쓰면서 옆에 두고 본다"이므로, 한 번에 보이는 기록 수가 곧 기능의 값이다.

### 2.2 캡처 입력: 두 줄 → **한 줄**

v4는 340px에서 `[날짜][시간]` / `[텍스트]` 두 줄로 감기게 설계했다(한 줄에 넣으면 텍스트 칸이 132px).
680px에서는 `[날짜][시간][한 일 추가]`가 **한 줄에 들어가고 텍스트 칸이 약 450px** 남는다.

**CSS를 바꿔서가 아니라 기존 `.quick-add{flex-wrap:wrap}` + 텍스트 `min-width:150px`가 알아서 푼 결과다** —
필요 폭 `100(날짜) + 62(시간) + 150(텍스트 최소) + 16(gap) = 328px`이 패널 폭 안에 들어가면 한 줄,
안 들어가면(패널 ~330px 이하) v4처럼 두 줄로 되돌아간다. **새 분기 코드 없음.**

### 2.3 날짜 헤더 합계: 우측 끝 → **시간 열과 세로 정렬** (유일한 CSS 신규 규칙)

```css
.day-head .day-sum{margin-left:auto; padding-right:33px; ...}   /* 33 = 🗑 25 + gap 6 + 단위 여백 2 */
```

패널이 넓어지면 날짜 라벨(좌)과 합계(우)가 680px 떨어져 **둘의 관계가 흐려진다.**
합계를 삭제 버튼 폭만큼 안으로 들여 **바로 아래 시간 칸들의 `h`와 세로로 맞추면**,
넓어진 폭이 빈 여백이 아니라 "이 열의 합계"라는 **표 구조**를 만든다.

- 이 규칙은 `dayGroupHtml`을 쓰는 **세 화면 전부**(작성 패널 / 대시보드 카드 / 한 일 기록 화면)에
  동일하게 적용된다 — 기록 행 구조가 셋 다 같으므로 정렬도 셋 다 맞는다.
- **QA 검증 기준**: 어느 화면이든 `4.5h` 같은 날짜 합계의 `h`가 그 아래 시간 입력칸의 `h`와 같은 x좌표에 있어야 한다.

### 2.4 일부러 **안 한** 것

- **패널 내부 패딩 확대(20px → 28px)**: 넓어졌으니 본문 카드(`26px 28px`)와 맞추자는 안을 검토했으나 기각.
  이건 조밀한 스크롤 목록이고, 8px 차이는 인지되지 않으면서 텍스트 폭만 16px 깎는다.
- **넓어진 자리에 새 정보 추가**(태그·프로젝트 연결·요약 등): v3에서 확정한
  "기록에 가능한 조작은 추가/수정/삭제 셋뿐, 항목당 부가 UI 없음" 원칙을 폭이 남는다는 이유로 깨지 않는다.

## 3. 트레이드오프 (투명하게)

### 3.1 우측 작성 폼이 986px → 916px로 **70px 좁아진다**

v2~v4 내내 986px로 고정돼 있던 값이다. 이번에 처음으로 줄어든다.

| | v4 | v5(1670px 화면) |
|---|---|---|
| 우측 컬럼 | 986px | **916px** |
| 행에 쓸 수 있는 폭 | 930px | **860px** (= 계산된 하한, 여유 0) |
| 제목 칸 — 배지 없는 행 | 338px | **268px** |
| 제목 칸 — 완료+이월 배지 동시 | 230px | **160px** (= `min-width` 하한) |

- **행이 두 줄로 접히는 일은 없다**(하한을 정확히 만족). 다만 **여유가 0**이라, 앞으로
  항목 행에 무언가를 더 붙이면(새 배지·새 칸) 그 즉시 하한이 올라가 이 계산을 다시 해야 한다.
  → **이 문서를 항목 행 변경 시의 체크포인트로 남긴다.**
- 160px는 13px 폰트에서 한글 약 10자다. 배지 2개가 붙은 행에서 긴 프로젝트명은 잘려 보인다
  (입력칸이라 클릭하면 스크롤되어 다 읽고 수정할 수 있다).
- **이걸 감수한 이유**: 사용자가 명시적으로 키우라고 한 건 좌측이고, 우측은 이미 검증된 하한이 있다.
  하한을 넘지 않는 선에서 여유분을 전부 좌측에 넘기는 게 요청에 대한 최대치다.

### 3.2 "정확히 2배"가 모든 화면에서 보장되지는 않는다

680px는 **뷰포트 1670px 이상에서만** 나온다. 사용자의 주 모니터(2560px)에서는 요청대로 정확히 2배다.
1920@125% 같은 환경에서는 530px(+56%)가 그 화면의 물리적 최대치다 —
**더 키우려면 항목 행이 두 줄로 깨지는 것을 허용해야 하고, 그건 이 화면의 기본 시각 규칙(v2~v4에서 세 번 지킨)이다.**

> 만약 사용자가 **"그 화면에서도 무조건 680px"** 을 원한다면, 선택지는 둘뿐이고 둘 다 별도 결정이 필요하다:
> (a) 항목 행이 두 줄로 접히는 것을 허용한다(시각 규칙 폐기), 또는
> (b) 항목 행 자체를 줄인다 — 예: 이월/완료 배지를 아이콘·점으로 축약(−88px), 일감번호 칸 축소.
> **(b)는 실현 가능한 방향이지만 항목 행의 정보 표시를 바꾸는 별도 라운드다.** 이번엔 손대지 않았다.

## 5. frontend 경계 (승인 후 착수 시 — **아직 착수 금지**)

v4 §7에 아래를 더한다. **이번 라운드는 CSS 3줄 + 미디어쿼리 1줄이 전부이므로 이식 난이도는 가장 낮다.**

- `static/css/app.css`에 옮길 값: `body.wide main{max-width:1670px}` / `.header-inner{max-width:1650px}` /
  `.split{grid-template-columns:minmax(0,680px) minmax(916px,1fr)}` / 스택 미디어쿼리 `max-width:1280px` /
  `.day-head .day-sum{padding-right:33px}`.
- **`916px`와 `680px`는 임의의 값이 아니다** — §1의 계산에서 나온 값이다. 반올림하거나 "적당히" 바꾸지 말 것.
  특히 `minmax(916px,1fr)`의 916을 `0`으로 바꾸면(습관적으로 `minmax(0,1fr)`을 쓰기 쉽다)
  **좁은 화면에서 항목 행이 조용히 두 줄로 깨진다.**
- 목업 `<script>`의 상태 배열·이벤트 위임은 여전히 **이식하지 않는다**(기존 원칙).
- 이 변경은 레이아웃뿐이라 htmx 배선·프래그먼트 경계에 영향이 없다.

## 6. 목업에서 확인해볼 동선 (v4 §8에 더해)

1. 창을 최대화(2560 모니터) → hero `신규 작성` → **왼쪽 패널이 v4의 딱 2배로 넓어졌는지**
2. 같은 화면에서 **오른쪽 항목 행이 여전히 한 줄인지** — 특히 `완료`+`이월` 배지가 같이 붙은 행
3. 긴 기록("GTPP 결제 로그 분석 — 타임아웃 원인 확인")이 **한 줄에 들어가는지**(v4에선 2줄)
4. 패널 하단 입력이 `[날짜][시간][텍스트]` **한 줄**인지(v4에선 두 줄)
5. 날짜 헤더의 `4.5h`가 **아래 시간 칸들의 `h`와 세로로 맞는지** — 세 화면 모두
6. **창을 좌우로 천천히 줄여보기**: 패널이 연속적으로 줄어들되 **오른쪽 행은 끝까지 한 줄**을 유지하는지,
   1280px 부근에서 세로 스택으로 넘어가는지
7. `숨기기` → 1140px 복귀 / 대시보드·히스토리 탭은 폭 변화 없음

| 1 | 1536px급 화면에서 **530px가 아니라 무조건 680px**을 원하는가? | 원한다면 §3.2 (b)(배지 축약으로 행 최소 폭 낮추기)를 **별도 라운드**로. 지금 구조를 그대로 두고 강행하면 행이 깨진다 |
