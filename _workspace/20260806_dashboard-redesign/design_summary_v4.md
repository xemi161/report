## 1. 투입시간 필드 — 세 화면에 같은 컴포넌트로

### 1.1 왜 새 컴포넌트를 만들지 않았나

주간보고 항목 행에 이미 `.hours-input`이 있다 — **56px, 우측정렬, 뒤에 `h`/`시간` 단위, 평소엔 테두리 없이 텍스트처럼 있다가 hover/focus에서만 강조.** 일일 기록의 시간도 의미가 정확히 같은 값(그 일에 들어간 시간)이므로 **동일 클래스를 그대로 재사용**했다. 좁은 패널을 이유로 44px짜리 변형을 만드는 안을 검토했지만 기각 — 화면마다 시간 칸 폭이 다르면 "저기 있던 그 칸"이라는 인식이 깨지고, 계산해보니 340px 패널에서도 56px이 들어간다(§2).

CSS 변경은 기존 스코프 목록에 `.daily-item`을 **추가**한 것뿐이다:

```css
.row-main input[...], .simple-row input[...], .daily-item input[type=number]{ ... }
/* hover / focus 규칙도 동일하게 3줄 추가 */
.daily-item .hours-input{flex:none; margin-top:1px;}   /* 텍스트가 두 줄로 감겨도 시간은 첫 줄에 고정 */
```

### 1.2 선택 입력이다 (강제하지 않는다)

- `placeholder="-"` — 빈 값이 "0시간"이 아니라 **"안 적음"** 으로 읽히게 한다.
- 데모 데이터에도 시간이 빈 기록을 일부러 섞어 뒀다(`신입 온보딩 질문 대응`) — 그게 정상 상태다.
- 저장 값은 빈 문자열(→ backend `null`), `0`이 아니다.
- 근거: 이 기능의 목적은 "가볍게 흘려 적기"다. 필수로 만들면 정확히 재야 한다는 압박이 생겨 기록 자체를 안 하게 된다.

### 1.3 하루 합계 — **채택**

날짜 헤더(`.day-head`) 우측 끝에 `4.5h`처럼 붙인다(`margin-left:auto`, 굵게, `tabular-nums`).

- **채택 이유**: 시간을 적는 목적이 "주 끝에 다시 기억해내지 않기"인데, 날짜별 합계는 거기에 더해 **기록이 빠진 날을 스스로 드러낸다** — "수요일이 1.5h네, 그날 뭐 더 했었는데" 가 곧 회수 행동이 된다. 데이터는 이미 날짜로 그룹핑돼 있어 추가 비용이 0이다.
- **합계가 0이면 아예 렌더하지 않는다.** `0h`를 들이밀면 "채워야 할 빈칸"으로 읽혀 §1.2의 선택 입력 성격과 충돌한다.
- 같은 규칙을 상위 단위에도 적용: 작성 패널 제목 칩 `12건 · 21h`, 대시보드 카드 제목 칩 `3건 · 5.5h`, 대시보드 하단 요약 `이번 주 기록 12건 · 21h`, 기록 화면 월 통계 `기록된 시간 21h`. 전부 시간이 0이면 건수만 남는다.
- 통계 라벨은 **"기록된 시간"** — "총 투입시간"이 아니다. 선택 입력이라 합계는 항상 부분값이고, 주간보고의 총 투입시간(맨위크 계산 기준)과 혼동되면 안 된다.

### 1.4 화면별 배치

| 위치 | 배치 |
|---|---|
| **기록 행**(세 화면 공통) | `[텍스트 textarea][시간 56px][h][🗑]` — 텍스트가 여러 줄로 감겨도 시간·단위·삭제는 첫 줄 정렬 유지 |
| **대시보드 빠른 입력** | `[텍스트 flex:1][시간 62px][+ 추가]` — 시간을 **텍스트 뒤**에, 폭 고정. 캡처의 주인공은 텍스트다. 시간 칸에서 Enter를 쳐도 추가된다(Tab→Enter 흐름) |
| **작성 화면 패널 입력** | `[날짜 select][시간 62px]` 윗줄 / `[텍스트]` 아랫줄 전체 폭. `.quick-add{flex-wrap:wrap}` + 텍스트 `min-width:150px`로 340px에서 자연 줄바꿈. 셋을 한 줄에 넣으면 텍스트 칸이 132px로 쥐어짜인다 |
| **기록 화면 입력** | `[날짜 input type=date][시간][텍스트]` — 한 줄(카드 폭 ~1030px). 여긴 한 달을 넘나들므로 select가 아니라 date input |

## 2. 패널 폭 340px / `body.wide` 1400px 으로 복귀

v3에서 체크박스가 사라진 만큼 340→300px, 확장폭 1400→1360px으로 줄였는데, **시간 칸이 그 자리를 도로 가져간다.**

```
증가분: 시간 56 + 단위 h 10 + gap 6·2 = 약 40px  →  300 + 40 = 340px
확장폭: 986(우측 컬럼, v2·v3와 동일) + 340 + 18(gap) + 56(패딩) = 1400px
```

- **우측 작성 폼 컬럼의 실폭 986px은 v2·v3와 픽셀 단위로 동일하다** — 늘어난 40px는 전부 좌측 패널이 가져간다. v3 §2.2의 "행이 두 줄로 접히면 안 된다"는 계산(이월+완료 배지 동시 860px 필요)은 그대로 만족.
- 340px 패널에서 기록 텍스트에 남는 폭: `340 − 40(패딩) − 56 − 10 − 25(🗑) − 18(gap) = 191px`. 긴 예시("GTPP 결제 로그 분석 — 타임아웃 원인 확인")가 2줄로 감기고 잘리지 않는다(v3 §1.2 목적 유지).
- **QA 검증 기준**: 대시보드·히스토리·"패널 숨김" 상태의 작성 화면은 여전히 **1140px**. `body.wide`는 작성 탭 + 패널 표시 중일 때만 붙는다.

## 3. "한 일 기록" 화면 — IA 판단

### 3.1 결론: **4번째 탭을 만들지 않고, 히스토리 탭 안의 두 번째 뷰로 넣는다**

```
[대시보드] [작성] [히스토리]          ← 헤더 탭은 3개 그대로
                     └─ 화면 안 서브 세그먼트: [과거 보고서 · 6] [한 일 기록 · 12]
```

### 3.2 근거 (탭 승격을 검토했고 기각한 이유)

오케스트레이터가 "매일 들여다볼 수 있으니 탭 승격 근거가 생겼다"고 봤는데, 넷을 따져 기각했다.

1. **이름이 충돌한다.** 헤더에 `히스토리`와 `기록`이 나란히 서면 한국어로 사실상 동의어다. 사용자가 매번 "어느 쪽이 보고서고 어느 쪽이 메모지?"를 생각해야 하는 탭 바는 그 자체로 실패다. 이건 스타일 취향이 아니라 IA 결함이다.
2. **성격이 같다.** 두 목록 다 "지난 것을 최신순으로 훑고, 누르면 그 시점으로 들어간다". 다른 탭이 아니라 **같은 탭의 두 뷰**가 정확한 관계다.
3. **"매일 들여다보는" 자리는 이 화면이 아니다.** 기록을 *적는* 지점은 이미 둘이다 — 대시보드 캡처 카드(첫 진입 화면), 작성 패널. 새 화면은 적는 곳이 아니라 **찾아보는** 곳이다. 매일 여는 건 대시보드지 이 화면이 아니므로, 상시 노출 슬롯을 요구할 빈도 근거가 약하다.
4. **히스토리 탭은 이 앱에서 가장 빈 탭이었다** — 카드 목록 하나가 전부였고 자체 툴바도 없었다. 새 뷰가 그 공백을 채운다.

> **기각한 대안**: 대시보드 카드에서만 진입하는 별도 페이지("전체 N개 보기" 패턴). 진입점이 하나뿐이라, 대시보드를 지나쳐 작성 탭에 있는 사람이 "지난달에 뭐 했더라"를 찾으려면 대시보드로 돌아가야 한다. 탭 바에 상시 흔적을 남기는 편이 낫다.

**진입점 2개**: (a) 히스토리 탭 → `한 일 기록` 세그먼트, (b) 대시보드 "오늘 한 일" 카드 하단 `전체 기록 보기`.

### 3.3 시간 축: **월 단위** (주 페이저 재사용 아님)

주차 페이저를 재사용하는 안을 먼저 검토했고 기각했다 — **작성 화면 좌측 패널이 이미 주 단위 열람을 하고 있어서, 그대로 옮기면 새 화면이 기존 기능의 복사본이 되고 "쭉 보기"라는 요구 자체를 못 채운다.**

- 한 달치를 **한 화면에 세로로 쭉** 깔고, 넘기는 조작은 한 달에 한 번만 일어나게 한다(주 페이저 대비 조작 1/4).
- 무한 스크롤은 기각 — 서버 렌더+htmx 구조에 페이지네이션 상태를 끌고 들어오는 비용이 이 규모의 사내 도구에 과하고, 월 경계가 "지난달에 뭐 했더라"라는 실제 사고 단위와 맞는다.
- 페이저는 **헤더가 아니라 화면 안**(`.pager.inline`)에 둔다. 헤더 페이저는 주(보고서) 축 전용이고, 축이 다른 페이저 둘이 같은 자리에 번갈아 나타나면 무엇을 넘기는 중인지 모호해진다. 컴포넌트 스타일은 헤더 페이저와 동일.
- 데이터가 있는 달의 범위를 벗어나면 이전/다음 버튼이 `disabled`.

### 3.4 화면 구성

```
[◀ 2026년 8월 ▶]                        [🔍 기록 검색 (예: GTPP)]
[기록 12건] [기록된 시간 21h] [기록한 날 6일]
┌ card ─────────────────────────────────────────────┐
│ [날짜 ▦][시간][한 일 추가 (Enter)]                 │
│ 08.13 (목)  오늘                            2h    │
│   결제 배치 실패 건 재처리        [2] h      🗑    │
│ 08.12 (수)                                 4.5h   │
│   GTPP 외부 연계사 일정 협의    [1.5] h      🗑    │
│   OTP 재발송 예외 처리            [3] h      🗑    │
│   ⋮                                               │
└───────────────────────────────────────────────────┘
주간보고를 쓸 때 참고하는 개인 기록입니다. 내보내는 .md 파일에는 포함되지 않습니다.
```

- **한 카드에 그 달 전체.** 날짜별로 카드를 쪼개면 "쭉 훑는" 연속면이 끊긴다. 날짜 구분은 이미 있는 `.day-group` / `.day-head`를 그대로 재사용.
- **정렬은 최신 위(내림차순).** 작성 패널이 금→목 오름차순인 것과 **다르다** — 패널은 한 주를 처음부터 끝까지 읽는 자리고, 여기는 최근에서 거슬러 올라가는 자리다. 과거 보고서 목록(최신순)과 축이 같다. → **QA는 이 차이를 버그로 잡지 말 것.**
- **CRUD는 좌측 패널과 완전 동일** — 텍스트 수정(textarea 자동 확장), 시간 수정, 삭제, 추가. 그 이상은 없다.
- **승격 장치 없음** — v3에서 확정한 "체크·화살표·대상 셀렉트 없음" 원칙이 이 화면에도 그대로 적용된다. 여기서 기록을 골라 주간보고 항목으로 만드는 UI는 존재하지 않는다.
- 하단 안내 문구가 `.md` 미포함을 명시한다(사용자가 여기서 "이거 보고에 나가나?"를 가장 많이 물을 화면이므로).
- 그 달 밖 날짜로 기록을 추가하면 화면이 그 달로 따라간다 — 적었는데 사라지는 일이 없어야 한다.

### 3.5 검색 — **제안, 뺄 수 있음**

`기록 검색` 입력이 비어 있지 않으면 **월 범위를 무시하고 전체 기간에서** 텍스트 부분일치로 찾아 최신순으로 보여준다. 이때 통계 3칸 대신 `전체 기간에서 "GTPP" — 7건` 스코프 배너가 뜨고, 날짜 라벨이 `2026.08.10 (월)`로 연도까지 붙으며, 빠른 입력은 숨는다(필터된 화면에 추가하면 어디로 들어갔는지 안 보임).

> ⚠️ **이건 사용자가 요청한 게 아니라 내가 얹은 제안이다.** "쭉 보기"의 실제 용례 절반이 "그거 언제 했더라"라서 월 페이저만으로는 안 잡힌다고 봤고, backend 비용도 `LIKE` 쿼리 하나뿐이라 넣었다. **검토 때 불필요하다고 판단하면 빼면 된다** — 화면의 나머지 구조는 그대로 성립한다.

### 3.6 부수 변경: 헤더 탭에서 건수를 뺐다

`히스토리 · 6` → `히스토리`. 탭이 두 뷰를 담게 되면서 숫자 하나가 무엇의 건수인지 모호해졌다. 건수는 안쪽 세그먼트가 각각 들고 있다(`과거 보고서 · 6` / `한 일 기록 · 12`).

### 3.7 대시보드 카드 하단 링크가 둘이 됐다

`이번 주 기록 12건 · 21h` ┈ `[전체 기록 보기] [주간보고 쓰면서 보기 →]`

`주간보고 쓰면서 보기 →`를 없애고 새 링크로 대체하는 안을 검토했으나 유지했다 — 그 링크는 "옆에 두고 보면서 쓴다"는 이 기능의 핵심 동선을 알리는 유일한 문구다(v3 §4). 좌측 컬럼이 충분히 넓어(~750px) 둘이 나란히 들어가고, 화살표가 붙은 쪽이 주 동선임을 형태로 구분한다.

## 4. backend 파급 — v3 §5에 얹는 차분

### 4.1 엔티티: `hours` 한 칸 추가

```
DailyNote
  id        Long
  workDate  LocalDate
  text      String
  hours     BigDecimal   -- ★ v4 신규. nullable. 0이 아니라 null이 "안 적음"이다
  createdAt Instant
```

- **`BigDecimal`** — 기존 `ReportItem.hours`와 같은 타입. 0.5 단위 입력(`step="0.5"`)이 들어오고, 화면 표기는 뒷자리 0을 떼야 하므로 `ReportItem.hoursDisplay()`와 같은 방식의 표기 헬퍼가 필요하다(`8.00` → `8`). CLAUDE.md에 이미 기록된 함정.
- **여전히 `ReportItem`·`WeeklyReport`·`Project` 어느 것과도 연관관계 없음.** FK 없음, 무결성 훅 없음.
- 합계는 서버에서 낸다(`SUM`이든 스트림이든) — null은 0으로 취급하되, **합이 0이면 화면에 아무것도 안 그린다**(§1.3).
- **맨위크·주간보고 통계에 절대 섞이지 않는다.** 일일 기록의 시간은 참고값이고 보고서 총 투입시간과 별개다. `computeTotals` 계열 로직에 들어가면 안 된다. → **QA 검증 기준**: 기록에 시간을 넣어도 작성 탭 상단 `총 투입시간`/`맨위크`/대시보드 `최근 2주 평균 맨위크`가 변하지 않아야 한다.

### 4.2 조회 쿼리: 하나 더 필요하다 (v3는 하나로 충분했다)

| 용도 | 쿼리 |
|---|---|
| 대시보드 카드 · 작성 패널 (기존) | `findByWorkDateBetweenOrderByWorkDateAscIdAsc(start, start+6)` |
| **기록 화면 — 월 열람 (신규)** | `findByWorkDateBetweenOrderByWorkDateDescIdAsc(월초, 월말)` — **정렬 방향이 반대다**(§3.4). 같은 메서드를 `Sort` 인자로 받게 해도 되고 별도로 둬도 된다 |
| **기록 화면 — 검색 (신규, §3.5 채택 시)** | `findByTextContainingIgnoreCaseOrderByWorkDateDescIdAsc(q)` |

- **페이지네이션 불필요.** 한 달 최대 ~60건(하루 2~3건 × 22 영업일). 실제로 화면이 통째로 그 달을 렌더하므로 페이징은 오히려 "쭉 보기"를 깬다.
- 검색은 전체 기간이라 데이터가 누적되면 커지지만, 1인용 로컬 H2에 몇 년 치라도 수천 건 수준이다. `workDate` 인덱스 하나로 충분하고 `text` 인덱스는 불필요.
- `MdExportService` / `docs/weekly-report-md-schema.md` — **여전히 손댈 것 없음**(§0).

### 4.3 라우팅 (frontend·backend 공통 참고)

기록 화면은 히스토리 탭 안이므로 `/history?view=records&month=2026-08&q=...` 형태의 **쿼리 파라미터**로 상태를 들고 다니는 게 기존 `/entry?week=yyyy-MM-dd` 관례와 맞는다. 새 최상위 라우트를 만들지 않는다.

## 5. 로드맵 §2 "파트원 개인 일정관리"에 대한 메모

사용자 답변("일정기록은 오늘 한 일로 관리할 수 있을거 같고")으로 **v3 열린 질문 1이 닫혔다** — v3는 "별개로 두기"를 추천했으나 사용자가 **반대로 결정**했다. 일일 기록이 그 역할을 겸한다.

따라서 `docs/2026-08-06-role-roadmap.md` §2는 **실질적으로 해소됐다.** 단, 해소된 범위를 정확히 적어둔다:

| 로드맵 §2가 암시하던 것 | v4에서 |
|---|---|
| **회고형** — 뭘 했는지 날짜별로 남기고 나중에 훑어보기 | ✅ 해소 (일일 기록 + §3 열람 화면 + §1 시간) |
| **전망형** — "내일 할 일", 예정 일정, 계획 | ❌ **포함 안 됨** |

사용자는 *"오늘 한 일로 관리할 수 있을 것 같다"* 고 했지 전망형 계획 기능을 요청한 게 아니다. v2·v3에서 세운 **완료형 어휘 방어선**(UI 어디에도 "일정/할 일/예정"을 쓰지 않는다)은 v4에서도 그대로다 — 새 화면 이름도 `한 일 기록`이고, 어떤 문구도 미래를 암시하지 않는다.

> **문서 자체는 이번에 건드리지 않았다.** 로드맵 §2 갱신은 사용자 승인 후 docs-sync가 처리할 일이다.

## 7. frontend 경계 (승인 후 착수 시)

**아직 착수 금지.** 승인되면 v3 §8에 아래를 더해 전달할 것:

- 목업 `<script>`의 `DAILY` 배열·`histSub`/`recMonth`/`recQuery` 상태·이벤트 위임은 **이식하지 않는다**(기존 원칙). 서버 렌더 + 쿼리 파라미터(§4.3)가 그 책임을 대체한다.
- **시간 인라인 수정은 텍스트와 동일하게 `hx-trigger="change" hx-swap="none"`** — 포커스 유지.
  → 그래서 **날짜 헤더 합계·카드 제목 칩·하단 요약은 서버가 갱신해주지 못한다.** 목업의 `refreshDaySum()` / `refreshDashDailyTotals()`가 하는 일을 `static/js/app.js`가 클라이언트에서 해야 한다(완료율 100% "완료" 배지, textarea 자동 높이와 같은 자리). 이게 부담이면 시간 수정만 `hx-swap="outerHTML"`로 그 `.day-group`을 다시 그리는 절충도 가능하다 — 대신 편집 중 포커스가 날아간다.
- **기록 화면 검색**(§3.5 채택 시)은 `hx-trigger="keyup changed delay:300ms"` + 목록 영역만 교체. 목업처럼 화면 전체를 다시 그리면 커서 위치를 손으로 복원해야 한다.
- 기록 추가/삭제는 여전히 "구조가 바뀌는 동작" → 해당 뷰 전체 재렌더 + `hx-swap="outerHTML"`.
- 대시보드 빠른 입력은 v3대로 `hx-swap="beforeend"` + 요약 줄 `hx-swap-oob`.
