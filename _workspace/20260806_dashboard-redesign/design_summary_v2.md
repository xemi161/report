## 0. 왜 승인된 시안을 다시 열었나

사용자가 새 아이디어 3개를 냈고, 셋이 합쳐지면 대시보드가 "무엇을 위한 화면인가"가 바뀐다.

1. **일일 업무 리스트** — 매일 그날 한 일을 짧게 기록해두고 그걸 보며 주간보고를 쓴다(실제로 엑셀로 하던 방식).
   동기: 바쁠 때 주 초반에 뭘 했는지 기억이 안 나 누락된다.
2. **체크박스로 주간보고에 등록** — 자동 합산이 아니라 사람이 "이건 보고감"이라 판단해 승격시키는 반자동.
3. **작성 화면 좌우 분할** — 좌: 일일 리스트, 우: 주간보고 작성. 좌에서 체크하면 우에 추가.

**핵심 변화**: 기존 대시보드는 *주 단위*로 들르는 화면을 전제했다(이번 주 상태 → 내 페이스 → 과거 보고서).
일일 기록이 생기면 이 앱에 **하루 단위 방문**이 생긴다. 랜딩 화면의 1순위가 "보고서 쓰기"에서
"오늘 한 일 적어두기"로 바뀌므로, 대시보드 구성을 다시 짠 것이 이번 작업의 본체다.

## 1. 대시보드 재구성 — 무엇이 바뀌었나

### 변경 전(v1, 승인본)
```
① 이번 주 카드 (full width hero)
② [최근 2주 평균 맨위크 330px] [진행중인 프로젝트 1fr]
③ 과거 보고서 최근 5개
```

### 변경 후(v2)
```
① 이번 주 카드 (full width hero)          ← 유지. 문구만 추가(§1.3)
② [오늘 한 일 1fr]  [최근 2주 평균 맨위크 340px]
                    [진행중인 프로젝트    340px]   ← 우측에 세로로 스택
③ 과거 보고서 최근 5개                     ← 그대로
```

### 1.1 무엇을 왜 이 순서로 두었나

- **hero는 그대로 최상단**. 일일 기록이 아무리 자주 쓰여도 이 앱의 목적어는 여전히 주간보고다.
  "이번 주가 몇 월 몇 주이고 지금 어떤 상태인가 + 강한 CTA 하나"라는 v1의 역할은 손대지 않았다.
  세로로 ~110px밖에 안 써서 아래 카드들을 밀어내지도 않는다.
- **오늘 한 일 카드가 좌측·넓은 칸**. 하루에도 여러 번 쓰이는 유일한 요소이므로 접근 비용이 가장 낮아야 한다.
  기존에 좌측 좁은 칸을 쓰던 맨위크 카드는 **주 단위로만 보는 추세 지표**라, 진행중 프로젝트와 함께
  우측 사이드바(`.dash-side`)로 묶었다. 즉 **좌 = 매일 만지는 것 / 우 = 주 단위로 훑는 것**으로 축을 갈랐다.
- **그리드 비율이 뒤집혔다**: `330px | 1fr` → `1fr | 340px`. v1에서 진행중 프로젝트가 넓은 칸을 쓰던 걸
  좁은 칸으로 옮겼는데, 프로젝트 행(이름+티켓 pill+%+진행바+최근 보고 주차)은 세로로 쌓이는 구조라
  340px에서도 정보가 깨지지 않는다.
- **과거 보고서 5개는 그대로**. 건드릴 이유가 없어 v1 결정(제출본만, 5개, `전체 N개 보기 →`)을 유지했다.
  개수를 줄이면 v1에서 사용자가 확정한 내용을 근거 없이 뒤집는 셈이라 손대지 않았다.

### 1.2 제거하거나 강등한 것 — 없음

v1의 4개 블록(hero / 맨위크 / 진행중 프로젝트 / 과거 보고서)은 **전부 남아 있다.** 하나가 추가되고
배치만 바뀌었다. 승인된 결정을 되돌리지 않는 게 이번 재검토의 전제였다.

### 1.3 hero에 추가된 한 줄 (일일 기록과의 연결점)

미반영 기록이 있을 때만 hero에 문구가 붙는다. 없으면 아무것도 안 붙는다(잔소리 방지).

| 이번 주 상태 | 미반영 있음 | 표시 |
|---|---|---|
| 미작성 | 있음 | "이번 주에 기록한 일 **N건**이 아직 주간보고에 반영되지 않았습니다. 작성을 시작하면 옆에 두고 하나씩 옮길 수 있습니다." |
| 미작성 | 없음 | 기존 문구("아직 작성을 시작하지 않았습니다 …") 그대로 |
| 작성중/제출됨 | 있음 | 기존 통계 3종 아래에 "일일 기록 **N건**이 아직 주간보고에 반영되지 않았습니다." |
| 작성중/제출됨 | 없음 | 기존 통계 3종만 |

**검증 기준**: N은 `--warn-fg`(주황), 나머지 문장은 `--text-muted`. 배지가 아니라 문장 안의 `<b>`다.

## 2. 일일 기록을 어디서 입력하는가 — (c) 둘 다, 단 역할이 다르다

요청받은 후보는 (a) 작성 화면 좌측만 / (b) 대시보드 빠른 입력만 / (c) 둘 다 였다. **(c)를 골랐다.**
다만 "둘 다 똑같이 되게" 한 게 아니라 **역할을 갈랐다.**

> **기록은 어디서나, 승격은 작성 화면에서만.**

| | 대시보드 "오늘 한 일" | 작성 화면 좌측 "이번 주에 한 일" |
|---|---|---|
| 목적 | **캡처** — 일 끝날 때마다 한 줄 | **정리** — 주간보고로 옮기기 |
| 범위 | 오늘 + 최근 2일(`DASH_RECENT_DAYS=3`) | 그 주 7일(금~목) 전체 |
| 할 수 있는 것 | 추가 / 수정 / 삭제 | 추가 / 수정 / 삭제 + **체크(승격)** / 대상 변경 / 필터 |
| 체크박스 | **없음** | 있음 |

### 왜 (a) 작성 화면만으로는 안 되는가 (구조적 이유)

작성 화면은 `week` 파라미터에 매인 화면이고, **보고서가 없는 주는 빈 상태 화면**이다("작성 시작" 버튼).
일일 기록을 거기서만 받으면 *"오늘 한 일 한 줄 적으려면 먼저 주간보고 초안을 만들어야 한다"* 가 된다.
이건 취향 문제가 아니라 흐름이 막히는 문제다. 그래서 캡처 지점은 앱을 열면 바로 나오는 대시보드에 둔다
(앱 진입 → 타이핑 → 끝, 두 동작).

### 왜 대시보드에는 체크박스를 두지 않는가

승격은 **어디로 보낼지**를 정하는 일인데(§4), 대시보드에는 옮겨 담을 주간보고가 화면에 없다.
목적지가 안 보이는 상태에서 목적지를 고르게 하면 결과를 확인할 수 없다. 대시보드 기록 행에는
이미 올라간 것만 `반영됨` 칩(`--good-bg`/`--good-fg`)으로 읽기전용 표시한다.

### 빠져 있는 것을 채우는 장치

- 대시보드 카드 하단: `이번 주 N건 · 미반영 M건` + `작성 화면에서 정리하기 →`(`.link-more`)
- 작성 화면 좌측 패널: 날짜 선택이 붙은 입력 한 벌을 하단에 상시 노출 → **지난 날에 빠뜨린 기록도 채울 수 있다**
  (금~목 7일이 셀렉트에 들어간다). 그래서 "그날 못 적었으면 영영 못 적는" 구멍이 없다.

## 3. 작성 화면 좌우 분할

```
[ 이번 주에 한 일 340px ]  [ 통계 3종 / 제출 배너 / 프로젝트·개발·기타·휴가 카드 / 제출 버튼 ]
   sticky, 자체 스크롤            (= 기존 작성 화면 전체가 그대로 우측 컬럼으로 들어감)
```

- **좌 = 재료, 우 = 결과물.** 체크가 왼쪽에서 오른쪽으로 흐르는 방향을 레이아웃으로 못박았다.
- **좌측 패널은 `position:sticky`** (`top:84px`, `max-height:calc(100vh - 108px)`, 자체 스크롤).
  작성 폼이 길어져도 체크박스가 늘 보여야 한다.
- **패널 접기 가능**: 패널 헤더 우측 `숨기기` → 기존 단일 컬럼 화면과 완전히 동일해진다.
  숨긴 상태에선 상단에 `한 일 기록 보기` 고스트 버튼. **일일 기록을 안 쓰는 사람에게 강요되지 않는다.**
- **1040px 이하에서 세로 스택** — 좌측 패널이 위, 작성 폼이 아래. sticky도 해제된다.
- 통계 3종(총 투입시간/맨위크/항목 수)은 **우측 컬럼 안**에 둔다. 그 숫자들은 주간보고의 속성이지
  화면 전체의 속성이 아니다.

### ⚠️ 페이지 폭을 넓혔다 (이번 라운드에서 새로 생긴 유일한 전역 변경)

분할을 켜면 우측 컬럼이 좁아져 **항목 행이 두 줄로 접힌다.** 항목 행 1줄의 최소 폭은
티켓 132 + 제목 160 + 구분 96 + 시간 56 + 일수 40 + 진행률 86 + 버튼/단위/gap ≈ **750px**인데,
기존 `main{max-width:1140px}`에서 분할 시 우측 가용폭은 ≈650px이라 모자란다.
"한 줄 = 한 항목"은 이 화면의 기본 시각 규칙이므로, **좌우 분할이 켜진 동안에만** 페이지를 넓힌다.

```css
body.wide main{max-width:1400px;}
body.wide .header-inner{max-width:1380px;}
```

`body.wide`는 **작성 탭 + 패널 표시 중**일 때만 붙는다(패널을 숨기거나 다른 탭으로 가면 즉시 1140px로 복귀).
→ **frontend 검증 기준**: 대시보드/히스토리와 "패널 숨김" 상태의 작성 화면은 기존과 픽셀 단위로 같은 폭이어야 한다.

## 4. 체크 → 주간보고 등록의 실제 동작

오케스트레이터가 제안한 "제목이 미리 채워진 새 항목 생성" 방향을 채택했고, **목적지 문제**만 다르게 풀었다.

### 4.1 체크하는 순간 무슨 일이 일어나는가

1. 기록 텍스트가 **제목**으로 들어간 항목이 즉시 생성된다. 티켓/구분/시간/일수/완료율은 **비어 있다**.
2. 오른쪽의 그 행으로 **스크롤 + 1.3초 강조(`--accent-soft` 배경 페이드)** 되고 제목 칸에 포커스가 간다.
3. 왼쪽 기록 행에는 `→ [대상 셀렉트]`가 붙는다(pill 형태, `--accent-soft`). 여기서 바로 다른 곳으로 옮길 수 있다.

**모달을 쓰지 않는다.** 보고 쓰는 날 5~6건을 연달아 체크하는 게 정상 사용인데, 매번 모달이 뜨면 흐름이 끊긴다.

### 4.2 목적지 문제 — 일일 기록엔 프로젝트 개념이 없다 (⚠️ 요청받은 갭)

주간보고 그룹은 **프로젝트 / 개발 / 기타 / 휴가**인데, 자유 텍스트 한 줄에는 그 정보가 없다.
기록 시점에 프로젝트를 묻는 건 기각했다 — "일 끝날 때마다 짧게"라는 이 기능의 존재 이유를 정면으로 해친다.
**결정을 승격 시점으로 미루되, 기본값을 추측해서 채운다:**

| 상황 | 기본 대상 |
|---|---|
| 기록 텍스트에 그 주 프로젝트명이 포함됨 | **그 프로젝트 카드** (예: "GTPP 결제 로그 분석" → GTPP 카드) |
| 그 외 전부 | **개발 그룹** |

- 단순 `contains` 문자열 매칭이다. 틀려도 대상 셀렉트로 한 번에 옮길 수 있어 되돌리기 비용이 0에 가깝다.
- **휴가 그룹은 승격 대상에서 제외**했다(날짜·시간 구조가 자유 텍스트와 안 맞는다). 셀렉트에도 안 나온다.
- **프로젝트를 새로 만들지는 않는다** — 프로젝트는 이름+티켓번호가 필요한데 자유 텍스트에서 티켓을 지어낼 수 없다.
  그 주에 이미 있는 프로젝트 카드만 셀렉트에 나온다.

### 4.3 대상 변경(리타게팅)

셀렉트를 바꾸면 항목이 이동한다. **이미 입력한 구분/시간/일수/완료율/일정/비고는 그대로 옮겨간다.**
단 `기타` 그룹은 제목+시간뿐이라 나머지 필드는 자연히 버려진다(→ 되돌리면 복구 안 됨. §7 열린 질문 4).

### 4.4 체크 해제 / 삭제 / 수정의 의미 (⚠️ 셋을 구분할 것)

| 동작 | 결과 |
|---|---|
| **체크 해제** | 연결된 주간보고 항목을 **삭제**. 기록은 남고 미반영으로 돌아간다 |
| **기록 삭제**(휴지통) | 기록만 사라진다. **이미 올라간 주간보고 항목은 남는다** — 메모를 지웠다고 보고 내용이 지워지면 안 된다 |
| **기록 문구 수정** | 기록에만 반영. **이미 승격된 항목의 제목은 안 따라간다** — 승격은 *복사*이지 *동기화*가 아니다 |

⚠️ **체크 해제는 데이터 손실 위험이 있다.** 시간·완료율을 이미 채운 항목을 무심코 언체크하면 그게 날아간다.
목업은 확인 없이 바로 지우지만, **실제 앱에서는 연결 항목에 값이 입력돼 있으면 확인을 받아야 한다**(§7 열린 질문 3).

### 4.5 그 밖의 상태 규칙 (QA 검증 기준)

- **보고서가 없는 주(`status=empty`)**: 좌측 패널은 보이고 기록 추가/수정도 되지만 **체크박스는 disabled**
  (opacity .35). 안내 문구: "보고서 작성을 시작하면 여기서 체크해 옮길 수 있습니다."
- **제출된 주(`status=submitted`)**: 체크박스 **활성**. 제출=비잠금 정책과 일관된다.
- **필터**: `전체 N` / `미반영 M` 토글(pill). 미반영만 걸러 보는 게 누락 확인의 주 동선.
- **날짜 그룹**: 기록이 있는 날 + (이번 주면) 오늘만 표시. 빈 주말 행으로 목록을 늘리지 않는다.
  한 주는 **금~목** 순서(이 앱의 주 정의)이며 오름차순으로 나열된다.
- **오늘 표시**: 날짜 헤더에 `오늘` 칩(`--accent-soft`).
- **반영 상태 색**: 반영됨 = `--good-bg`/`--good-fg`(초록), 미반영 건수 = `--warn-fg`(주황).
  기존 규약(완료=초록, 이월=주황)과 어긋나지 않는다.

## 5. 탭은 늘리지 않았다 (3탭 유지)

**일일 기록 전용 탭을 만들지 않았다.** 자문한 내용:

- 일일 기록은 **항상 주간보고를 위한 재료**다. 독립 탭을 만들면 "주간보고와 무관하게 기록을 열람하는 화면"이
  생기는데, 아무도 요구하지 않았고 §6의 개인 일정관리와 경계가 흐려진다.
- **과거 기록 열람 경로는 이미 공짜로 생긴다** — 작성 탭에서 주차 페이저를 뒤로 넘기면
  그 주의 일일 기록이 좌측 패널에 그대로 나온다(목업에서 8월 1주로 넘겨보면 확인 가능).

따라서 v1에서 확정된 `대시보드 · 작성 · 히스토리` 3탭은 그대로다.

## 6. ⚠️ "개인 일정관리"와는 별개로 두었다 — 사용자 결정 대기

`docs/2026-08-06-role-roadmap.md` §2에 **"파트원 개인 일정관리"** 라는 별개 아이디어가 스펙 없이 남아 있다.
이번 "일일 업무 리스트"와 **합치지 않았다.** 성격이 다르다고 판단했기 때문이다:

| | 일일 기록(이번 것) | 개인 일정관리(로드맵 §2) |
|---|---|---|
| 시간 방향 | **회고적** — 이미 한 일 | **전망적**(추정) — 앞으로 할 일 |
| 목적 | 주간보고 작성 시 누락 방지 | 미정 |
| 스펙 | 이 문서 | 없음 |

**설계에 심어둔 방어선**: UI 문구를 전부 **완료형("한 일")** 으로 통일했다 — 카드 제목 `오늘 한 일`,
패널 제목 `이번 주에 한 일`, 입력 placeholder `방금 끝낸 일을 짧게 적어두세요`.
"일정", "할 일", "예정" 같은 전망형 어휘를 의도적으로 쓰지 않았다.
→ 나중에 전망형 기능이 별도로 들어와도 **이름이 충돌하지 않는다.**

이 둘이 같은 기능인지 다른 기능인지는 **사용자가 결정할 사항**이다(§7 열린 질문 1).

## 8. backend 파급 (⚠️ 메모만 — 이번 라운드에서 구현/합의된 것 없음)

**backend 에이전트와 아직 상의하지 않았다.** 아래는 설계에서 파생되는 요구사항 정리이며,
승인 후 backend가 실현 가능성/비용을 확인해야 한다.

### 8.1 새 엔티티가 필요하다 — `ReportItem`으로는 표현 안 됨

```
DailyNote (가칭)
  id
  workDate    LocalDate     -- 기록 대상 날짜 (작성 시각이 아님: 어제 걸 오늘 적을 수 있다)
  text        String        -- 자유 텍스트 한 줄
  createdAt   Instant
  promotedItem  ReportItem   (nullable, 승격 시 연결)
```

- **소속 주는 저장하지 않고 `workDate`에서 파생**시킬 것을 권한다 — 이 앱의 주는 금~목이라 이미
  `WeekLabelService`에 규칙이 있다. `weekStart`를 중복 저장하면 주 정의가 바뀔 때 동기화 버그가 생긴다.
  조회 성능은 `workDate` 인덱스 + 범위 조회로 충분하다(주당 최대 수십 건).
- 대시보드/작성 화면 모두 **"기간 [start, start+6] 사이의 DailyNote 목록"** 하나면 된다.

### 8.2 "체크해서 등록"이 정확히 무엇을 만드는가

| 대상 | 만들어지는 것 |
|---|---|
| 개발 | `ReportItem(group=DEV, title=text, ticket=null, phase=null, hours=null, days=null, completion=null)` |
| 프로젝트 | 그 `Project`에 붙는 `ReportItem`. 제목=text, 티켓은 **프로젝트가 이미 갖고 있는 값**을 따른다 |
| 기타 | `ReportItem(group=ETC, title=text, hours=null)` |
| 휴가 | **불가**(셀렉트에 없음) |

### 8.3 ⚠️ 미결 사항 하나를 강제로 밀어낸다 — 개발 그룹 티켓 필수 여부

CLAUDE.md "다음에 할 일"의 첫 항목(**"개발 그룹의 티켓번호 필수 여부"**)이 이 기능 때문에 더는 미룰 수 없게 된다.
승격으로 만들어지는 개발 항목은 **항상 티켓이 비어 있다.** 현재 제출 검증(project/dev 모두 티켓 필수)이 유지되면
체크로 만든 항목은 전부 제출을 막는다 — 그러면 이 기능 자체가 성립하지 않는다.
→ **dev 그룹 티켓을 optional로 푸는 방향으로 결정되어야 이 설계가 동작한다.**
(마침 승인된 목업엔 티켓 없는 개발 항목 "사내 위키 정리" 예시가 이미 있고, md v2 포맷도 티켓 없는 줄을 지원한다.)

### 8.4 연결 무결성

- **`ReportItem`이 작성 화면에서 직접 삭제될 때** `DailyNote.promotedItem`을 null로 되돌려야 한다.
  안 그러면 체크박스가 거짓말을 한다(체크돼 있는데 주간보고엔 없음). FK `ON DELETE SET NULL` 또는 서비스 훅 필요.
- 기록 삭제는 `ReportItem`을 건드리지 않는다(§4.4).
- 승격 시 제목은 **복사**다. 이후 양쪽이 독립적으로 바뀐다(동기화 없음).

### 8.5 md 내보내기 — 변경 없음

일일 기록은 `.md`에 **나가지 않는다.** `MdExportService`도 `docs/weekly-report-md-schema.md`도 손댈 것이 없다.
(§7 열린 질문 5에서 사용자가 뒤집으면 그때 스키마 v3 논의)

## 9. frontend 경계 (승인 후 착수 시)

**아직 착수 금지.** 승인되면 아래를 함께 전달할 것:

- 목업의 `<script>` 상태 배열/이벤트 위임 로직은 **이식하지 않는다**(기존 원칙 그대로).
  `DAILY` 배열·`promoteEntry`/`demoteEntry`/`retargetEntry`는 "이 동작이 이런 결과를 낳아야 한다"는
  명세를 눈으로 보여주는 장치일 뿐이다.
- **승격/해제/대상변경/기록추가/기록삭제/필터전환은 전부 "구조가 바뀌는 동작"** →
  기존 규약대로 `#writeView` **전체**를 다시 렌더해 `hx-swap="outerHTML"`로 갈아끼운다.
  좌측 패널이 `#writeView` 안에 있으므로 카드별 건수·통계·미반영 건수가 한 번에 맞는다.
  (목업도 같은 방식으로 동작하도록 짰다 — `renderWrite()` 전체 재호출)
- **기록 문구 인라인 수정만 `hx-trigger="change" hx-swap="none"`** — 포커스 유지 목적, 기존 인라인 필드와 동일.
- **대시보드 빠른 입력**은 예외적으로 전체 재렌더가 아깝다. 목업은 카드를 다시 그리고 포커스를 되돌리지만,
  실제 앱에서는 목록에 `hx-swap="beforeend"`로 행만 덧붙이고 입력값을 비우는 편이 낫다(포커스가 아예 안 날아감).
  단 그러면 하단 `이번 주 N건 · 미반영 M건`이 낡으므로 `hx-swap-oob`로 같이 갱신할 것.
- **승격 후 강조(flash) + 스크롤**은 서버가 못 하는 클라이언트 동작이라 `static/js/app.js` 담당
  (완료율 100% "완료" 배지와 같은 자리).
- v1 §6의 주의(작성 탭 통계는 인라인 편집 시 `hx-swap="none"`이라 낡음 → `app.js` 클라이언트 계산)는 **그대로 유효**.
